§1게임 개요

코어 루프 — 하루 = 정보를 사서 위험을 줄이는 경영

시간대플레이어가 하는 일
아침 06–09이벤트 NPC(대장장이·무기상·수수께끼 상자 등) 응대, 09:00 의뢰판 갱신
낮 09–18방문한 모험가에게 던전 배정 + 무기 대여. 점술·수색·대화로 숨은 스탯/특성을 공개하고 성공률을 올림
저녁 18–21전령 보고 — 모험 결과 정산(수수료 7% + 대여료 10% ± 특성), 재료 회수
밤 21:00자동 일시정지 → 다음 날. 주말엔 주간 의뢰 판정, 미달 시 벌금

실시간 1초 = 게임 3분, 배속 조절 가능. 게임오버(파산)되면 회차가 끝나고 유산(영구 업그레이드)이 남아 다음 회차가 조금 쉬워지는 로그라이트 구조입니다. 40주 캠페인 이후는 난이도 등급이 붙은 엔드리스 의뢰가 이어집니다.

1.0 콘텐츠 규모

  • 무기 178종 · 던전 28종 · 재료 96종 · 액티브 아이템 30종 · 주간 의뢰 56종 · 던전 이벤트 97종
  • 모험가 페르소나 20종 + 네임드 8명, 특성 16종, 아침 이벤트 NPC 9종
  • 유산 업그레이드 20종, 대장간(강화·진화·재부여·분해·제작)
  • 리더보드(일수 기준), 닉네임, 기기 이전, 계정 초기화, 강제 업데이트
매일 바뀌는 던전 3개 선택
모험가 방문 — 정보 공개 후 배정
정산 — 수수료 구조가 그대로 보임
대장간 강화 — 부가효과 5종
설계의 중심 질문 — "정보를 사는 비용이 성공률 상승으로 회수되는가?" 이 게임의 모든 골드는 모험 성공에서 나오므로, 점술·수색·대화·무기 가격을 전부 모험 1회 순수입(R) 단위로 정의했습니다(§3-3). 상급 플레이어는 정보를 써서 R 자체가 커지고(약 1,100G), 초급은 정보를 안 써서 R이 작습니다(약 600G) — 실력 격차가 가격이 아니라 R에 녹아 있게 만든 것이 밸런스 설계의 핵심입니다.

§2아키텍처와 저장 계층

4계층 구조 — "Manager는 View를 모른다"

호출규칙
View → Controller도메인 매니저는 반드시 Controller 경유
View → DataManager정적 SO 카탈로그, 읽기 전용만 허용
View → AnalyticsManager관측 전용(상태 미변경)이라 직통 허용 — 컨트롤러 없는 View의 btn_clicked
Manager → View/Controller절대 금지. Manager는 event Action<>만 노출

거대 매니저는 기능별 partial로 분할 — AdventureManager 7파일 3,127줄(Calculations · EventProcessor · Sequence · HeraldReport · Mood), VisitorManager 5파일, Insight 5파일.

데이터 접근 원칙 — "ID로 굽고, 참조로 복원"

RuntimeInstance는 정적 SO를 참조로 직접 들고, 저장 시에만 ID 문자열로 굽습니다. RuntimeInstance는 DataManager를 모르며, 복원은 각 도메인 매니저의 Initialize(GameData)가 맡습니다.

// 굽기 — Utils/SaveDataConverter.cs
weaponDataID  = instance.weaponData.StaticID,          // SO 참조 → ID
dungeonDataID = instance.dungeon?.StaticID ?? "unknown",
rentedWeaponInstanceID = instance.rentedWeapon?.instanceID,

// 복원 — Systems/InventoryManager.cs:32 LoadFromGameData
var weaponData = DataManager.Instance.GetWeapon(saveData.weaponDataID);
if (weaponData == null) continue;                      // 폐기된 ID는 스킵
var effects = ReifyEffectsFromSave(saveData.effects);
ownedWeapons.Add(new WeaponInstance(weaponData, effects, saveData));

DataManager의 판정 기준: "이 메서드가 게임 규칙을 아는가(→ 도메인 매니저), 필드 값만 보는가(→ DataManager)". 예: GetEnforceMaterialByGrade는 규칙이라 BlacksmithManager로.

초기화 순서의 단일 진입점

GameManager([DefaultExecutionOrder(-100)])의 InitializeManagers()가 21개 매니저를 의존 순서로 초기화합니다: Inventory → … → Visitor → Adventure(모험가·무기가 먼저 있어야 진행 중 모험 복원) → … → Tutorial(맨 끝).

저장 계층 규약 3가지

문서 원문: "데이터 손실 버그가 반복적으로 나왔던 지점이라 공통 장치로 고정해 두었다."

규약구현
원자적 쓰기SaveManager.WriteAllTextAtomic — .tmp에 쓰고 File.Replace, 직전본은 .bak. 로드 시 본 파일 손상 → .bak 복구, 손상본은 .corrupt-타임스탬프로 보존
확정 직후 저장SaveAfterCommittedAction(reason) — 강화·상자·모험 출발 등 도박성 결과 확정 직후 저장해 강제 종료 세이브스컴 차단
로드 후 sanity passRepairLoadedGameData() — 복원 실패로 드롭된 모험의 isRented/isAdventuring 해제, 고아 아이템 반환

유산(PlayerData) 로드는 LoadDataStatus(Success / Missing / RestoredFromBackup / Corrupted)를 함께 반환 — Corrupted면 빈 데이터로 조용히 확정하지 않고 클라우드 복구·안내를 거칩니다.

§3밸런스 시뮬레이터 — 밸런싱을 실측으로 ★

문제"무기 3,000G가 비싼지 싼지 판단할 근거가 없어, 조정할 때마다 임의 수치를 골랐다." 목표를 '생존 주차' 같은 종속변수에 걸어두니 A를 고치면 B가 깨지는 두더지 잡기가 됐습니다.
접근게임 로직을 헤드리스로 돌리는 시뮬레이터(5,026줄)를 만들고, 모든 가격을 "모험 1회 순수입 R의 배수"로 읽는 기준 체계를 세웠습니다. 수치는 100% 실제 SO 에셋에서 읽습니다.
결과페르소나 3층 통과율 96 / 70 / 33%로 레벨디자인 합격선(95↑/70/40↓) 달성. 밸런스 변경 35건 전부 before/after 리포트 첨부. 리포트 255개 생성.

3-1. 설계 — 미러 로직 + 실제 에셋 + 결정론

  • 수치는 에셋, 공식은 미러. SimBundle.Load()가 Config SO 15종과 던전·무기·의뢰·모험가 데이터를 AssetDatabase로 통째로 읽습니다. 그래서 PriceTierConfig 값을 바꾸면 시뮬 코드는 손댈 필요가 없습니다. 런타임 MonoBehaviour 매니저는 호출하지 않고 계산식만 출처 주석을 달아 재구현했으며, 순수 static 유틸(StatCurve, TypeAdvantage)은 그대로 공유합니다.
  • 페르소나 3종(상급/중급/초급) — 차이는 정보 사용량 하나뿐. 판정은 SimWorld가 실제 수식으로 하고 페르소나는 선택만 합니다.
  • RNG 스트림 분리 — 메인/특성/점술/네임드/엔드리스 5개 시드를 따로 둡니다. 새 시스템을 미러링할 때 전용 rng를 쓰므로 그 축을 OFF로 끈 런이 도입 이전 코드와 비트 단위로 동일합니다. 이걸로 "새 시스템이 결과를 바꿨는가"를 무결성 A/B로 검증합니다.
  • 회차 반복 — 폐업 시 유산 획득 → 다음 회차(시드당 최대 5회). 유산 20종 단독 효과 스윕은 같은 시드끼리 짝지은 차이의 중앙값(paired median)을 씁니다 — 독립 비교는 시드 경로 발산만으로 10% 흔들려 효과가 묻히기 때문입니다.
// SimCore.cs:700-704 — 축별 독립 RNG 스트림
rng      = new Random(seed*977 + persona.Name[0] + (runIndex-1)*7919);
traitRng = new Random(seed*733 + ...);   // 특성 롤
seerRng  = new Random(seed*509 + ...);   // 점술
namedRng = new Random(seed*331 + ...);   // 네임드 스폰/재방문

3-3. R 기준 체계 — 가격을 "모험 몇 회분"으로 읽기

R = 모험 1회 성공 시 순수입. 이 게임의 모든 골드는 모험에서 나오므로 모든 가격을 R의 배수로 정의하고, 조정 위계를 고정했습니다.

1차  R 확정         던전 보상 × 수수료 — 다른 모든 것의 기준점
2차  가격 = R 배수   무기 1.8R~30R / 수색 0.3R / 점술 0.6R / 재부여 ~6R
3차  압박 = 수입 비율 벌금 (1200 + 1300w)
4차  페르소나 격차   생존 주차는 조정 대상이 아니라 "검증 대상"

부수 효과: R이 실력 지표를 겸합니다 — 상급자 R≈1,100G, 중급≈700G. 상성을 맞춰 팁 수수료를 받기 때문에 정보의 가치가 R에 이미 녹아 있습니다.

§4UGS 라이브옵스 — 클라이언트를 믿지 않는 설계 ★

문제1인 개발 모바일 게임에 리더보드·닉네임·기기 이전·밴이 필요했지만 전용 서버를 운영할 여력은 없었습니다. 클라이언트가 쓰는 값은 전부 위조 가능하다는 전제로 시작했습니다.
접근Cloud Save의 Protected access class(클라 읽기만, Cloud Code만 쓰기)를 신뢰 경계로 삼고, 판정이 필요한 모든 쓰기를 Cloud Code 11개 함수로 옮겼습니다. 서버 함수는 git이 단일 원본이고 CI가 배포합니다.
결과리더보드 4단계 검증, 서버 스탬프 세이브 동기화, 24h 복구 코드, 밴 3중 검사, 어드민 사이트(pytest 273줄)까지 DB 없이 운영. 정식 출시 후 운영 중.

4-1. 리더보드 점수 제출 — 4단계 서버 검증

  1. 타입/범위 — 양의 정수, ≤ 9999
  2. 밴 검사 — Protected의 banned/banUntil 재확인 (에러 2006)
  3. 세션 토큰 대조 + 재사용 차단 — startGameSession이 서버에서 만든 토큰을 Protected에 저장, 제출 시 대조하고 sessionTokenUsed로 Replay 차단. 사용 처리는 읽어둔 writeLock으로 조건부 갱신 → 동시 제출(TOCTOU) 시 한쪽만 성공
  4. 시간 검증 — 세션 경과 시간 ≥ claimedDays × 30초
"검증하지 않기로 한" 결정도 코드에 남겼습니다 (submitLeaderboardScore.js:125-148). claimedDays와 클라우드 playerData.currentDay를 대조해 거부하던 로직을 로그만 남기도록 바꿨습니다. 둘 다 클라이언트가 쓰는 값이라 치터는 저장본을 먼저 위조하면 통과하는 반면, 정상 유저는 일자 경계에서 업로드가 한 번만 늦어도 거부당해 기록을 영구히 잃습니다. "막지 못하는 치터 vs 잃는 정상 유저"를 저울질한 판단입니다.

4-2. 닉네임 — 서버 검증 풀세트

길이 2~12 · 정규식 ^[가-힣a-zA-Z0-9_]+$ · 욕설 필터는 NFKC 정규화 + 소문자화 후 매칭(전각/호환문자 우회 차단), 금칙어는 SO에서 스크립트로 JS에 자동 인라인. 변경 횟수는 writeLock 조건부 증가로 동시 요청 회피 차단. 리더보드 표시 직전 서버가 <>를 제거해 TMP rich-text 주입도 막습니다.

4-3. 세이브 동기화 — 시계는 서버 것만 믿는다

uploadSave가 저장과 동시에 서버 시각 스탬프를 기록하고, 클라이언트는 자기 마지막 업로드 스탬프만 기억합니다. 기기 시간 조작으로 오래된 저장이 최신으로 오판되는 일이 없습니다.

4-4. 기기 이전 · 밴

  • 복구 코드 — "playerId-secret", 24h 만료, 1회용. secret 불일치와 데이터 없음을 같은 에러코드로 응답해 계정 존재 여부 오라클을 차단. 원 기기는 30초 폴링으로 사용 감지 후 전체 wipe.
  • 밴 — source of truth는 Protected 3키. 검사는 앱 실행 · 재연결 · 점수 제출(실질 차단점) 3중. SDK가 에러코드 2006을 9009로 뭉개는 경우가 있어 메시지 문자열에서 JSON을 정규식 추출하는 우회까지 넣었습니다.
  • 어드민 사이트 — DB 없는 stateless MVP: 어드민이 죽어도 Unity Dashboard에서 같은 키를 직접 조작 가능. Google OAuth + 이메일 화이트리스트(비면 fail-closed), 502 변환 시 detail 축소로 시크릿 누출 방지. pytest로 밴 서비스·인증 경계 커버.

5-2. 다국어 — 프리팹 1,109참조를 건드리지 않고 4개 언어

출발점 문자열 약 2,300개가 전량 하드코딩. 전 UI가 한글 전용 폰트 Maplestory Light SDF 하나를 82파일 1,109곳에서 참조 — 가나·한자 글리프가 없어 ja/zh는 렌더링 자체가 불가능했습니다.

해결 ① 폰트 폴백 체인 (코드 약 10줄)

Asset Table로 폰트를 스왑하면 머티리얼 프리셋까지 흔들려 기각. 대신 배정 폰트는 그대로 두고 ja/zh 폰트를 폴백으로 추가, 로케일 변경 시 폴백 순서만 재배열합니다(ja → [JP, SC], zh → [SC, JP]). 이유는 Han unification — ja/zh가 공유하는 한자 코드포인트는 폴백 1순위 폰트 자형으로 그려지므로 순서가 곧 자형입니다.

이 프로젝트에서 배운 것

  • 측정할 수 없는 것은 조정할 수 없다. 시뮬레이터 이전의 밸런싱은 매번 임의 수치였습니다. 도구를 만든 뒤 "지표가 0이면 밸런스 결론 전에 봇부터 의심하라" 같은 함정 체크리스트까지 쌓였고, 결정의 근거가 남기 시작했습니다.
  • 클라이언트가 쓰는 값은 판정에 쓰지 않는다. 서버 시각 스탬프, Protected 키, writeLock 조건부 갱신 — 이 세 가지로 대부분의 위조·경합이 정리됐습니다. 반대로 "정상 유저가 잃는 검증"은 빼는 것이 맞다는 것도 배웠습니다.
  • 실측이 계획을 뒤집으면 계획을 버린다. 다국어 아틀라스는 "릴리즈 전 Static 재베이크"가 최초 계획이었지만, 글리프 수를 실제로 세어 보니 4배 무거워지고도 목적을 못 이루는 안이었습니다.
  • 안전망은 사고를 맞고 자란다. 감사 스크립트의 REVIEW/UNKNOWN_SCRIPT 판정, 저장 규약 3가지, 배포 초안 탐지 — 전부 실제 사고 뒤에 추가된 것입니다. 그 경위를 문서에 남겨서 같은 사고를 두 번 맞지 않게 했습니다.
  • 다음에 다시 한다면 — 도메인 매니저의 계산 로직을 처음부터 MonoBehaviour 없는 순수 C#으로 분리해 EditMode 테스트와 시뮬레이터가 같은 코드를 쓰게 하겠습니다. 미러 이중 관리와 테스트 부재가 같은 뿌리에서 나왔기 때문입니다.
