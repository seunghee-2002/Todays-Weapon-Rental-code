# 일반 모험가 AdventurerData를 성별 2종 -> 스탯 집중축 페르소나 20종으로 전면 개편

> 기록: 2026-07-29 · 작성: /balance

## 근거 (왜)

기존 일반 모험가 SO 14종은 **실질 차이가 성별 2종뿐**이었다. 세 가지 문제가 겹쳐 있었다.

**1) 성별이 스탯 성향을 100% 노출했다.**
여성은 STR/LUK 0~70 · DEX/INT 30~100, 남성은 그 반대로 고정이라
**남성 모험가에게 INT 71 이상은 구조적으로 존재할 수 없었다.**
외형(성별)만 보면 스탯 성향이 확정되므로 통찰(InsightManager)이 파는 정보의 가치가 깎였다.

**2) 무기 타입 수요가 극단적으로 편중됐다.** (20만 회 시뮬, 성별 50:50)
도끼 25.1% / 활 21.9% / 단검 18.1% / 마도서 15.0% / 지팡이 12.3%로 상위 5종이 92%를 먹고
**검 4.1% / 수리검 3.1% / 석궁 0%** 였다. 무기 상점 8종 중 3종이 사실상 죽은 재고였다.
남성은 STR·LUK가 동시에 높아 검(STR 1.2)이 항상 도끼(1.5)·단검(LUK 1.3)에 밀렸다.

**3) SO의 `trait` 필드가 런타임에서 무시되고 있었다.**
AdventurerInstance.cs:128-131 (`Assets/_Projects/Scripts/Data/RuntimeInstance/AdventurerInstance.cs`)이
일반 모험가 특성을 `TraitType` 16종 균등 랜덤으로 다시 뽑는다.
SO에 배분해둔 7종은 에디터 프리뷰 창에서만 읽히는 죽은 데이터였다.

### 설계 규칙 (사용자 제안 -> 검증 후 확정)

성공률은 총합이 아니라 **최적 무기 점수**(`TypeAdvantage.GetStatScore` 최대값)가 결정한다
(AdventureManager.Calculations.cs:1003 (`Assets/_Projects/Scripts/Systems/AdventureManager/AdventureManager.Calculations.cs`) - `점수 / dungeon.baseStatThreshold`).
따라서 총합 목표를 집중도별로 다르게 잡아야 최적 점수가 대등해진다.

| 집중도 | 총합 목표 | 주스탯 폭 | 근거 |
|---|---|---|---|
| 1스탯 집중 | 187.5 | 45 | 계수 1.5짜리 주스탯에 몰아넣어 총합 손해를 상쇄. 폭이 넓어 상단 스파이크 발생 |
| 2스탯 집중 | 202.5 | 29~30 | 시너지 무기가 없어 총합 보상 필요. 폭이 좁아 안정적 |

검증: 1스탯형 187.5와 2스탯형 202.5의 최적 무기 점수가 각각 129.6 / 130.1로 거의 정확히 겹쳤다.
**분산은 주스탯 폭이 거의 단독으로 지배한다** (INT집중 기준 주폭 55 -> sd 21.5, 폭 35 -> 15.0, 폭 15 -> 8.8).
사용자 초안은 폭 합이 155 vs 145로 거의 같아 의도한 분산 차이가 나지 않아 주스탯 폭으로 규칙을 다시 못박았다.

**축별 파워 보정은 의도적으로 넣지 않았다.** 무기 계수 테이블에 STR+INT 시너지 무기가 없어
STR+INT 축이 구조적으로 약한데(125), 이 편차를 그대로 두는 것이 "꽝/당첨" 이 된다.

## 대상 시스템 (무엇을)

- **방문자 스폰**(`VisitorManager.CreateNormalAdventurerInstance`) — 일반 모험가 스탯 롤
- **모험 성공률/사망률**(`AdventureManager.Calculations`) — 스탯 점수가 임계값 대비로 들어감
- **기본 무기 배정**(`VisitorManager.CreateDefaultWeaponFor`) — 최적 70% / 차선 20% / 랜덤 10%
- **무기 상점 수요**(간접) — 어떤 타입을 빌려주려 하는지가 바뀜
- **외형 생성**(간접) — `AdventurerJobType` 은 `GetHighestStat()` 하나로 결정됨

## 시뮬 / 검증 근거

**프로젝트 BalanceSim은 돌리지 않았다.** `TypeAdvantage.GetStatScore` / `weaponStatMultipliers` /
`dungeon.baseStatThreshold` 를 그대로 옮긴 별도 스크립트로 스탯 점수 분포만 계산했다
(페르소나당 40,000회 x 20종 = 80만 롤). 골드·평판·R 지표는 이번 검증 범위 밖이다.

`SimCore.cs:2872`가 이미 SO의 range를 미러링하므로 시뮬레이터 코드 수정 없이 새 값을 읽는다.

## 기대 효과 / 리스크

**기대 효과**
- 성별로 스탯을 못 읽는다. 여 평균 132.3 / 남 133.2로 대칭이고 당첨·꽝이 양쪽에 고르게 분포한다.
- 죽은 재고였던 검·수리검이 각각 전용 축을 얻었다.
- 페르소나별 파워 편차(125~142.5)가 "이 손님이 좋은 손님인가" 판단 재료가 된다.

**리스크 / 미해결**
- ~~**석궁은 여전히 0%.**~~ -> **후속 조치로 해결됨.** 수리검 `(0.2, 0.9, 0.2, 0.9)` 이 석궁
  `(0.2, 0.9, 0.2, 0.8)` 을 성분별로 완전히 지배하던 구조 결함을, 비어 있던 STR+INT 쌍에 석궁을
  재배치해 해소했다(`0.9, 0.2, 0.9, 0.2`, 석궁 12.1%).
  상세: [[2026-07-29_석궁_스탯계수_STR_INT|석궁 스탯 계수 DEX+LUK -> STR+INT]].
  이에 따라 아래 "검 4.1 -> 9.9%" 와 무기 수요 표는 석궁 조정 **전** 기준 값이다.
- **지팡이 수요가 12.3% -> 7.0%로 줄었다.** 마도서와의 경쟁에서 밀린다. 필요하면 DEX+INT 축의
  부스탯 배분을 STR 최저로 고정해 지팡이 창을 넓힐 수 있다.
- **인구 전체 파워가 3% 낮아졌다.** Rare 던전 76.2% -> 73.9%. 던전 임계값은 사용자 결정으로 손대지 않았다.
- **개체 내 분산이 크게 줄었다** (sd 25.1 -> 11~21). 개별 모험가의 "대박 100 스탯" 빈도가 줄고
  대신 페르소나 간 편차가 그 역할을 대신한다. 체감이 다를 수 있어 플레이 확인이 필요하다.
- **진행 중 세이브가 깨진다.** staticID가 전부 바뀌어 기존 `gamedata.json` 의
  `adventurerDataID` 가 `DataManager.GetAdventurer()` 에서 not found 로 떨어진다. 세이브 삭제 필요.
- `VisitorConfig.normalAdventurerStatMin/Max`(10/70)는 **이전에도 지금도 죽은 값**이다.
  모든 일반 SO가 range를 갖고 있어 `VisitorManager.Spawn.cs:134` 의 `hasStatRange` 폴백에 걸리지 않는다. 이번에 손대지 않았다.
