- `Assets/_Projects/Scripts/Data/Enums/ResultItemType.cs` — **정당한 이유 있음.** enum과 함께 확장 클래스 `ResultItemTypeExtensions`(`FromMaterialType`)가 묶여 있어, "순수 enum만 모으는" `Enums.cs`에 넣기 부적절해 분리한 것.

## 0. 분석 방법 (오탐을 줄이기 위해)

단순 "메서드 한 번 안 보임"으로 판단하지 않고 다음을 모두 교차검증했습니다.

1. **타입/멤버 토큰 전수 인덱싱** — 전체 스크립트를 토큰화해 각 타입·public 멤버가 *선언 파일 외*에서 참조되는지 카운트
2. **씬/프리팹 GUID 교차검증** — MonoBehaviour는 코드 참조가 없어도 씬/프리팹에 부착돼 동작할 수 있으므로, `.cs.meta`의 GUID를 `.unity`/`.prefab`에서 검색
3. **인스펙터(UnityEvent) 연결 검증** — `m_MethodName:` 로 버튼 등에 연결된 핸들러인지 확인
4. **`[ContextMenu]` / `[CustomEditor]` / 확장메서드 / 부분클래스** 등 "이름이 호출부에 안 나타나는" 패턴을 수동 확인

> ⚠️ **사용자가 예시로 든 3개 파일(BlinkingIndicator, MaterialSlotUI, TrackMarker)은 실제로는 모두 살아있습니다.** 상세는 [5번 항목](#5-사용자-예시-정정--실제로는-살아있는-코드) 참조.

## 4. 이상한 코드 — 파일명 ≠ 클래스명 / 오타 🟠

Unity는 **MonoBehaviour·ScriptableObject의 파일명이 클래스명과 일치**해야 정상 동작합니다(콘솔 경고, 인스펙터 부착 실패 가능). 일반 클래스는 동작엔 무관하지만 혼란을 줍니다.

| 파일 | 클래스 | 종류 | 심각도 |
|---|---|---|---|
| `Assets/_Projects/Scripts/UI/Controllers/VisitorSideBarController.cs` | `VisitorSidebarController` (Side**b**ar) | **MonoBehaviour** (프리팹 부착됨) | 🔴 가장 위험 — 파일명을 클래스명과 일치시킬 것 권장 |
| `Assets/_Projects/Scripts/Data/Config/WeaponshopConfig.cs` | `WeaponShopConfig` (Weapon**S**hop) | **ScriptableObject** | 🟠 .asset은 GUID로 로드돼 당장은 동작하나 메뉴 생성/경고 위험 |
| `Assets/_Projects/Scripts/Data/RuntimeInstance/WeaponInstace.cs` | `WeaponInstance` | 일반 클래스 | 🟡 **파일명 오타("Insta**c**e", n 누락)** |
| `Assets/_Projects/Scripts/Data/StatData/AdventurerStatData.cs` | `AdventureStatData` (Adventure**r**? 불일치) | 일반 클래스 | 🟡 파일명/클래스명 한 글자 불일치 |
| `Assets/_Projects/Scripts/Editor/AdventurerPreviewWIndow.cs` | `AdventurerPreviewWindow` | EditorWindow | 🟡 **파일명 오타("W**I**ndow")** |

> 현재 빌드/실행이 되고 있다면 Windows의 대소문자 무시 파일시스템 덕분일 수 있습니다. 그래도 위험 신호이므로 파일명 정리를 권장합니다. (특히 MonoBehaviour인 첫 행)

## 6. 참고: "Dead 아님이지만 과다 노출" (private 권장, 낮은 우선순위)

호출은 되지만 **자기 클래스 안에서만** 쓰이는데 `public`인 멤버들 — 동작엔 문제없는 캡슐화 스멜. (일부는 직렬화/리플렉션/인터페이스 패턴상 public이 정당하므로 일괄 변경 금지, 개별 확인 필요)
