# 퍼널 (Funnel A~L)

> [!abstract] 한 줄 요약
> UGS 대시보드 **Analytics -> Funnels**에 등록할 전환율 정의. A~E가 필수, F~H가 다음 우선순위, I~L은 표본이 쌓인 뒤에 만든다.

## 등록 우선순위

- [ ] **A~E** — 우선 등록 (핵심 루프 + 튜토리얼)
- [ ] **F · G · H** — 여유가 되면 바로 (온보딩 / 재시작 / 경제 병목)
- [ ] **I · J · K** — 표본이 쌓인 뒤

---

## 등록 전 필독

> [!danger] 튜토리얼 1일차는 모든 퍼널에서 제외한다 (E 제외)
> `TutorialManager`의 진행 훅이 **52개**이고, 1일차에 무기 구매·제작·강화·진화·재부여·아침 이벤트·의뢰판·수색 파견·무기 대여·아이템 선물·던전 선택·점술·모험 출발·결과 확인·퀘스트·인벤토리를 **전부 강제로 통과시킨다.**
> 따라서 1일차 수치는 유저의 의지가 아니라 튜토리얼이 만든 것이며, 섞이면 전환율이 실제보다 높게 나온다.
>
> **퍼널 E를 제외한 모든 퍼널의 모든 Step에 `day` `Greater Than` `1` 필터를 건다.**
> 예외 2건 — **퍼널 F는 `day = 2`**, **퍼널 G는 필터 없음**.
>
> 같은 이유로 **B·C·D는 "발견/탐색"이 아니라 "재이용/실행 전환"을 재는 퍼널이다.** 튜토리얼이 이미 다 가르쳐줬으므로 최초 발견 시점은 측정 대상이 아니다.
>
> -> [[튜토리얼]]

> [!warning] Step마다 파라미터 필터를 반드시 걸 것
> `panel_opened` / `btn_clicked`는 이벤트 이름 하나에 모든 패널·버튼이 들어 있다. 각 Step에서 **`Add Parameter` -> `panel Equal To ...`** (버튼 단계는 `button`까지 2개)를 설정해야 한다. 필터 없이 이벤트만 지정하면 모든 패널 열림이 잡혀 퍼널이 무의미해진다.
>
> - 같은 이벤트를 여러 Step에 반복 사용하는 것은 허용된다(퍼널 E).
> - 전환 기간(conversion window) 설정은 없고 상단 날짜는 **조회 기간**이다. 며칠에 걸친 탐색을 보는 **퍼널 B는 조회 범위를 넓게** 잡아야 한다.

> [!tip] 설명문
> 각 퍼널의 `Describe the funnel you're creating` 란에는 아래 인용 블록을 그대로 붙여 넣는다.

## A — 모험 시작 전환율

**목표**: [[분석목표|G1, G9]]

```
panel_opened(adventure_dialog)                          [day > 1]
  -> btn_clicked(adventure_dialog, prepare_adventure)   [day > 1]
  -> panel_opened(adventure_preparation)                [day > 1]
  -> btn_clicked(adventure_preparation, start_adventure)[day > 1]
  -> adventure_started                                  [day > 1]
```

> 방문자 대화창을 연 유저가 실제로 모험을 출발시키기까지의 전환율.
> 대화 -> 준비 화면 -> 출발 3구간 중 어디서 포기하는지 본다.
> 이탈이 큰 구간이 곧 모험 준비 UI의 혼란 지점이다.

---

## B — 대장장이 기능 재이용률

**목표**: [[분석목표|G4]]

```
panel_opened(blacksmith)                     [day > 1]
  -> btn_clicked(blacksmith, panel_weapon)   [day > 1]
  -> btn_clicked(blacksmith, upgrade)        [day > 1]
  -> btn_clicked(blacksmith, reroll_open)    [day > 1]
```

> 튜토리얼에서 이미 배운 대장장이 기능을 이후에도 실제로 쓰는지 본다.
> 재부여(reroll_open) 도달률이 낮으면 배우긴 했어도 비용 대비 효용을 못 느끼거나 진입 동선이 깊다는 신호.
> 며칠에 걸쳐 일어나므로 조회 기간을 넓게 잡아야 한다.

- 탭 5종 구조가 아니라 **2패널 구조**이므로 실제 코드에 맞춰 재정의했다. -> [[버튼_이벤트#대장장이]]
- **"발견 순서"로는 쓸 수 없다** — 튜토리얼 2단계가 제작·강화·진화·재부여를 모두 강제 통과시키므로 발견율은 항상 100%다.

## C — 통찰 실행 전환율

**목표**: [[분석목표|G3]]

```
panel_opened(adventure_preparation)                 [day > 1]
  -> btn_clicked(adventure_preparation, tab_explore)[day > 1]
  -> btn_clicked(adventurer_talk, reveal_stat)      [day > 1]
  -> btn_clicked(adventurer_talk, test_proceed)     [day > 1]
```

> 모험 준비 화면에 들어온 유저가 통찰(스탯 테스트)을 실제로 실행하기까지의 전환율.
> 테스트를 고르고도 확인 패널에서 실행하지 않는 이탈(reveal_stat -> test_proceed)이 핵심 구간이며,
> 시간/유산 비용이 부담스러운지 판단하는 근거가 된다.

- 통찰 탭이 **기본 착지 탭**이라 `panel_opened(adventurer_talk)` 대신 실제 액션 버튼으로 측정한다. -> [[통찰_시스템]]

---

## D — 수색꾼 파견 전환율

**목표**: [[분석목표|G3, G8]]

```
panel_opened(quest_board)                          [day > 1]
  -> panel_opened(scout_dispatch)                  [day > 1]
  -> btn_clicked(scout_dispatch, dungeon_selected) [day > 1]
  -> btn_clicked(scout_dispatch, send_scout)       [day > 1]
  -> scout_sent                                    [day > 1]
```

> 의뢰판을 연 유저가 수색꾼 파견까지 도달하는 비율.
> 파견 화면(Phase 2)에 진입조차 안 하면 기능을 잊었거나 필요를 못 느끼는 것,
> 진입 후 파견을 안 하면 비용 부담이나 효용 불명이 원인이다.

- `scout_result` 패널이 코드에 없으므로 결과 확인율 대신 **파견까지의 전환율**로 측정한다.
- 의뢰판 Phase 1(던전 선택)은 나갈 수 없는 강제 구간이라 Step 1은 사실상 "그날 접속했는가"에 가깝다.

## E — 튜토리얼 진행

**목표**: [[분석목표|G27]] · **`day` 필터 없음** (유일하게 1일차를 재는 퍼널)

```
tutorial_step(step=1)
  -> tutorial_step(step=4)
  -> tutorial_step(step=8)
  -> tutorial_step(step=12)   <- 완료
```

> 1일차 튜토리얼 12단계 중 신규 유저가 어디서 이탈하는지 추적한다.
> 감소율이 가장 큰 구간이 곧 안내가 부족한 단계다.
> D1 리텐션과 직결되므로 우선순위가 가장 높다.

---

## F — 튜토리얼 이후 자율 루프 (온보딩) ★

**분류**: 온보딩 · **`day = 2` 필터** (Step 1~2에만)

```
panel_opened(adventure_dialog)  [day = 2]
  -> adventure_started          [day = 2]
  -> adventure_completed
  -> panel_opened(adventure_result)
```

> 튜토리얼이 끝난 2일차에 유저가 스스로 모험 한 바퀴를 도는지 본다.
> 퍼널 E가 "안내를 따라왔는가"라면 이것은 "안내 없이도 하는가"이며,
> E는 완주했는데 이 퍼널에서 끊기면 튜토리얼이 조작법만 가르치고 이유를 못 가르친 것이다.

> [!warning] `day` 필터는 Step 1~2에만 건다
> 저녁에 출발한 모험은 밤 9시를 넘겨 3일차에 완료될 수 있어, 완료·결과 단계까지 날짜로 묶으면 **정상 완주가 이탈로 잡힌다.** -> [[시간]]

- **이 퍼널만 `day > 1`이 아니라 `day = 2`다.** 재는 것이 "평상시 루프 전환율"이 아니라 **"튜토리얼 직후 자립하는가"**이기 때문이다. `day > 1`로 넓히면 오래 버틴 유저의 반복 플레이가 섞여 첫 자율 시도라는 의미가 사라진다.
- **첫 모험(1일차)은 이 퍼널로 보지 않는다** — 튜토리얼 5·6·9단계(PrepEnter / SendAdventure / AdventureResult)가 첫 모험을 통째로 강제하므로 퍼널 E와 같은 구간이 된다.

## G — 게임오버 후 재시작 회복 ★

**목표**: [[분석목표|G14]] 분해 · **필터 없음** (게임오버는 튜토리얼과 무관하고 발생 일차가 유저마다 다르다)

```
game_over
  -> panel_opened(legacy_upgrade)
  -> btn_clicked(legacy_upgrade, buy)
  -> game_start
```

> 폐업한 유저가 유산 업그레이드를 거쳐 다시 시작하기까지의 전환율.
> 유산 화면조차 안 열면 게임오버 연출이 재도전이 아닌 종료로 읽힌 것이고,
> 열고도 안 사면 유산이 부족하거나 업그레이드가 매력 없는 것이다.
> G14(재시작율)를 원인별로 쪼개서 본다.

-> [[유산_시스템]]

## H — 무기 상점 구매 전환 ★

**분류**: 경제 병목

```
panel_opened(weapon_shop)                     [day > 1]
  -> btn_clicked(weapon_shop, weapon_selected)[day > 1]
  -> btn_clicked(weapon_shop, purchase)       [day > 1]
  -> weapon_purchased                         [day > 1]
```

> 상점을 연 유저가 실제 구매까지 가는 비율.
> 구매 버튼을 눌렀는데 weapon_purchased가 없는 구간이 곧 골드 부족으로 실패한 케이스이며,
> 초반 경제가 빡빡한지 직접 보여주는 지표다.

-> [[무기점_시스템]] · [[경제]]

## I — 무기 대여 전환

**목표**: [[분석목표|G13]] 원인 규명

```
panel_opened(adventure_preparation)                  [day > 1]
  -> panel_opened(weapon_selection)                  [day > 1]
  -> btn_clicked(weapon_selection, weapon_card_click)[day > 1]
  -> btn_clicked(weapon_selection, weapon_selected)  [day > 1]
```

> 모험 준비에 들어온 유저가 무기를 직접 골라 대여하기까지의 전환율.
> 무기 선택 화면까지 갔는데 대여를 안 하면 인벤토리에 쓸 무기가 없거나 판단 근거가 부족한 것이다.
> G13(무기 직접 선택률)이 낮게 나올 때 원인을 좁히는 데 쓴다.

## J — 강화 완주율

**목표**: [[분석목표|G4]] 보조

```
panel_opened(blacksmith)                    [day > 1]
  -> btn_clicked(blacksmith, upgrade)       [day > 1]
  -> btn_clicked(blacksmith, enforce_weapon)[day > 1]
  -> blacksmith_enforce_done                [day > 1]
```

> 대장장이를 방문한 유저가 강화를 실제로 실행하기까지의 전환율.
> 확인창까지 열고 실행하지 않는 이탈(upgrade -> enforce_weapon)이 곧 비용 부담 구간이다.

-> [[무기_시스템]]

## K — 아침 이벤트 참여율

**목표**: [[분석목표|G6]] 보조

```
morning_event_shown              [day > 1]
  -> panel_opened(morning_event) [day > 1]
  -> morning_event_resolved      [day > 1]
```

> 아침 이벤트 NPC가 등장했을 때 유저가 끝까지 상대하는 비율.
> 등장했는데 패널조차 안 열면 존재를 놓친 것이고, 열고도 결정을 안 하면 선택지가 매력 없는 것이다.
> G6(수락률)의 분모 밖에서 새는 유저를 잡는다.

-> [[아침이벤트_시스템]]
