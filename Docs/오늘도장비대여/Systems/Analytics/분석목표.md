## 모험

관련 도메인 문서: [[모험_시스템]] · [[모험_UI]] · [[모험가_시스템]]

### G1 — 모험 UI 복잡도

> [!question] 방문자 대화 시작 후 모험을 보내기까지 몇 초 걸리는가?

- **측정** — `adventure_dialog`가 열린 시각부터 `adventure_started` 시각까지의 **실시간** 경과초. `start_adventure` 버튼이 G1의 종료점이다.
- **구현** — ✅ `panel_opened(adventure_dialog)` 시 `Time.realtimeSinceStartup`을 저장하고, `adventure_started` 발행 시 경과초를 계산한다 (`AnalyticsManager`).
- **왜 보는가** — 방문자 클릭 -> 대화 -> 준비 -> 시작까지 단계가 많다. 소요 시간이 길면 UI 혼란 구간이 있다는 신호다. 기능을 발견하지 못해 기본 무기로만 보내는 패턴과 교차 분석할 수 있다.
- **예상 로그** — `adventure_started { dialog_open_duration_sec: 18, weapon_is_player_selected: true, day: 3 }`

### G7 — 모험 성공률

> [!question] 던전별 평균 성공률은? 무기 등급 대비 성공률은?

- **측정** — `adventure_completed`에서 `dungeon_id` x `weapon_grade` x `outcome` 크로스 집계. 등급이 낮은 무기로 고난이도 던전에 가는 패턴도 함께 탐지된다.
- **구현** — ✅ `AdventureResult.isSuccess / isDeath / isRetreated / isGreatSuccess` 필드가 이미 존재하므로 `outcome`으로 매핑만 하면 된다.
- **왜 보는가** — 던전별·무기 등급별 성공률이 의도한 범위를 벗어나는 구간을 찾는 것이 밸런스 조정의 기준점이다.
- **예상 로그** — `adventure_completed { dungeon_id: "forest_02", outcome: "success", weapon_grade: 2, day: 5 }`

### G9 — 방문자 상호작용률

> [!question] 방문자가 스폰됐을 때 대화로 이어지는 비율은?

- **측정** — `visitor_spawned` 수 대비 `panel_opened(adventure_dialog)` 수를 같은 `day` 기준으로 비교한다.
- **구현** — ✅ `VisitorManager.OnVisitorSpawned`에서 `visitor_spawned` 발행, `UIManager.OpenPanel<AdventureDialogView>()`에서 `panel_opened` 발행.
- **왜 보는가** — 스폰됐는데 대화로 이어지지 않으면 대여 수익이 0이다. 비율이 낮으면 방문자 스프라이트 시인성 또는 클릭 영역 문제다.
- **예상 로그** — `visitor_spawned { adventurer_id: "adv_12", is_named: false, day: 4 }`

### G11 — 점술가 사용 빈도 및 효과

> [!question] 점술가를 얼마나 자주 쓰는가? 쓴 모험과 안 쓴 모험의 성공률 차이는?

- **측정** — `panel_opened(seer)` 횟수로 사용 빈도를, `adventure_completed`의 `seer_used=true` 그룹 vs `false` 그룹의 성공 비율 차이로 효과를 본다.
- **구현** — ✅ 구현됨. `seer_used`는 `AdventureInstance.seerUsed`에 **출발 시점 스냅샷**으로 저장한다(점술 결과가 일 단위로 초기화되므로). 세이브에 포함된다.
- **왜 보는가** — 점술가 비용(골드)을 냈는데 성공률 향상이 없다면 유저가 낭비로 인식하고 사용을 중단한다. 효과 검증 후 수치 조정의 기준으로 쓴다.
- **예상 로그** — `adventure_completed { seer_used: true, outcome: "success", dungeon_id: "dungeon_03", day: 6 }`

### G12 — 통찰 정보가 모험 성공에 미치는 영향

> [!question] 스탯·특성을 많이 공개할수록 모험 성공률이 높아지는가?

- **측정** — `adventure_completed.revealed_stat_count`(0~4) 구간별로 같은 이벤트의 `outcome` 비율을 비교한다. `trait_revealed=true` 그룹도 별도 비교.
- **구현** — ✅ 통찰 파라미터를 `adventure_started`와 `adventure_completed` **양쪽에 복사해서 발행**하므로 이벤트 간 조인이 필요 없다.
- **왜 보는가** — 통찰에 인게임 시간·유산을 투자할 실질적 가치가 있는지 데이터로 검증한다. 효과가 없으면 통찰 메커니즘 재설계가 필요하다.
- **예상 로그** — `adventure_started { revealed_stat_count: 3, trait_revealed: true, dungeon_id: "cave_01" }`

### G13 — 무기 대여 비율

> [!question] 플레이어가 직접 무기를 골라주는가, 기본 무기로 보내는가?

- **측정** — `adventure_started.weapon_is_player_selected` 비율. 낮으면 "무기 선택 UI에 진입하지 않는다"는 뜻이므로 G1과 결합해 준비 UI 복잡도를 확인한다.
- **구현** — ✅ 구현됨. `!AdventureInstance.isUsingDefaultWeapon`으로 계산하므로 별도 플래그가 필요 없다.
- **왜 보는가** — 직접 선택률이 낮으면 무기 선택 UI 진입이 어렵거나 기본 무기에 대한 신뢰가 높은 것이다. G1과 교차하면 시간 부족으로 넘어가는 패턴도 탐지된다.
- **예상 로그** — `adventure_started { weapon_is_player_selected: false, weapon_id: "default_sword", day: 2 }`

### G17 — 모험 결과 유형 분포

> [!question] 성공/실패/사망/후퇴 비율은? 어느 던전에서 무기 손실이 가장 많은가?

- **측정** — `adventure_completed.outcome` 분포 x `dungeon_id` 교차 집계. `outcome=retreat` 비율은 유저의 위험 회피 행동 지표로 별도 추적한다.
- **구현** — ✅ `AdventureResult`의 4개 bool 필드를 우선순위 순으로 `outcome` string에 매핑한다.
- **왜 보는가** — 사망률이 높은 던전 = 무기 손실이 집중되는 경제 타격 구간. 후퇴율은 유저의 위험 인지 능력 지표다. 두 가지의 밸런스 조정 방향이 서로 다르다.
- **예상 로그** — `adventure_completed { outcome: "death", dungeon_id: "lava_cave", weapon_grade: 1, is_named_adventurer: false, day: 7 }`

### G19 — 무기 타입 매칭 실천율

> [!question] 던전 방어 타입에 맞는 무기를 선택하는 비율은?

- **측정** — `adventure_started.armor_type_match` 비율. 매칭 여부 x 성공률 교차는 `adventure_completed.armor_type_match` x `outcome`으로 본다(조인 불필요).
- **구현** — ✅ `AdventurerInstance`의 선호 무기 타입과 `WeaponInstance`의 타입을 `adventure_started` 시점에 비교해 계산한다.
- **왜 보는가** — 타입 매칭은 팁 수익과 성공률에 영향을 주는 핵심 메커니즘이다. 실천율이 낮으면 정보가 눈에 띄지 않거나 방법을 모른다는 뜻 -> UI 또는 튜토리얼 개선.
- **예상 로그** — `adventure_started { armor_type_match: false, weapon_id: "axe_01", day: 4 }`

### G22 — 네임드 vs 일반 모험가 성공률

> [!question] 단골 네임드 모험가 관리가 실제로 성공률에 영향을 주는가?

- **측정** — `adventure_completed`의 `is_named_adventurer=true` 그룹 vs `false` 그룹의 `outcome` 분포 비교.
- **구현** — ✅ `AdventurerInstance.isNamed`가 이미 존재. `adventure_started`·`adventure_completed` 양쪽에 포함한다.
- **왜 보는가** — 단골 관리가 실제 성공률 향상으로 이어지는지 검증한다. 차이가 없다면 네임드 특성 보너스가 약하다는 신호다.
- **예상 로그** — `adventure_completed { is_named_adventurer: true, outcome: "success", dungeon_id: "cave_01", day: 9 }`

### G26 — 모험 결과 확인 지연 시간

> [!question] 모험 완료 후 결과를 얼마나 늦게 확인하는가?

- **측정** — `panel_opened(adventure_result).delay_real_min` 분포. 대부분이 0~1분이면 유저가 결과를 기다리지 않고 화면을 붙들고 있는 것 -> 모험 소요 시간 조정 검토.
- **구현** — ✅ `AdventureInstance.completedAtUtcTicks`(모험 완료 시 `DateTime.UtcNow.Ticks` 기록, 세이브 포함)와 현재 시각의 차이로 계산한다.
- **왜 보는가** — 유저가 결과창을 열기까지 실제로 얼마나 텀을 두는지가 모험 소요 시간 설계의 기준이 된다.
- **예상 로그** — `panel_opened { panel: "adventure_result", delay_real_min: 15, day: 5 }`

> [!danger] `Time.realtimeSinceStartup` 사용 금지
> 앱 재시작 시 리셋되므로 "앱 끄고 나중에 결과 확인" 패턴이 측정에서 통째로 빠진다. G26은 반드시 UTC ticks 기준으로 잰다.

## 대장장이

관련 도메인 문서: [[무기_시스템]] · [[무기_UI]]

### G4 — 대장장이 기능별 사용 빈도

> [!question] 강화/진화/해체/재련/제작 중 무엇을 가장 많이 쓰는가? 거의 안 쓰는 기능은?

- **측정** — Level 4 실행 이벤트(`blacksmith_*_done`) 5종을 **유저별 총 실행 횟수**로 집계해 기능별 평균 사용 횟수를 비교한다.
- **구현** — ✅ `BlacksmithManager`의 각 실행 메서드(`ExecuteEnforce`, `ExecuteEvolve` 등) 완료 시점에 발행. 5종 이벤트가 이미 정의돼 있다.
- **왜 보는가** — 거의 안 쓰이는 기능은 진입 장벽이 높거나 효과가 불분명하다는 뜻이다. `enforce` 20회 vs `reroll` 1회 같은 격차가 나오면 재련 UI 개선 신호.
- **예상 로그** — `blacksmith_enforce_done { weapon_id: "sw_01", weapon_grade: 2, level_before: 3, level_after: 4, success: true }`

### G21 — 강화 실패 후 재시도율

> [!question] 강화 실패 후 유산으로 재시도하는 비율은?

- **측정** — `blacksmith_enforce_done(success=false)` 이후 **동일 `session_id` 내** `btn_clicked(blacksmith, enforce_retry)` 발생 여부를 세션 단위 퍼널로 본다. 클라이언트 집계는 불필요하다.
- **구현** — ✅ Level 3 `enforce_retry` 이미 정의됨.
- **왜 보는가** — 재시도(유산 소비)를 안 한다면 비용이 너무 높거나 기능 존재를 모르는 것이다. G4와 달리 "실패 후 회복 행동"에 초점을 둔다.
- **예상 로그** — `blacksmith_enforce_done { success: false }` -> `btn_clicked { panel: "blacksmith", button: "enforce_retry", day: 8 }`

> [!tip] `enforce_retry`는 유산 차감보다 **먼저** 발행한다
> G21이 재는 것은 "재시도를 시도했는가"이지 "유산이 충분했는가"가 아니다.

### G23 — 대장장이 타입별 이용 빈도

> [!question] 비용절감/재료절감/성공률/분해 중 어떤 타입을 가장 자주 이용하는가?

- **측정** — `panel_opened(blacksmith).blacksmith_type` 분포. **스폰 빈도 불균형을 보정해서 해석할 것.**
- **구현** — ✅ `BlacksmithType` enum이 `CostReduction / MaterialReduction / SuccessRateBoost / DisassembleBoost` 4종으로 정의돼 있다. `BlacksmithManager.GetTypeAnalyticsName()`으로 변환해 전달한다.
- **왜 보는가** — 특정 타입에만 방문이 몰리면 나머지 타입의 효과가 약하거나 스폰 빈도가 불균형하다는 신호다.
- **예상 로그** — `panel_opened { panel: "blacksmith", blacksmith_type: "success_rate", day: 6 }`

### G5 — 퀘스트 난이도

> [!question] 퀘스트 발행일부터 클리어까지 며칠 걸렸는가? 실패(벌금) 비율은?

- **측정** — `quest_completed.days_to_complete` 분포로 난이도를, `quest_failed` 비율로 벌금 유발 퀘스트 유형을 파악한다. 퀘스트 ID별 평균 소요일을 비교하면 "적당히 도전적인" 퀘스트와 "불가능한" 퀘스트가 갈린다.
- **구현** — ✅ `QuestManager`에 `OnQuestCompleted`·`OnQuestFailed` 이벤트가 있고, `issue_day`·`complete_day` 모두 `QuestInstance`에서 추적 가능하다.
- **왜 보는가** — 특정 퀘스트에서 벌금 비율이 높다면 조건 완화가 필요하다.
- **예상 로그** — `quest_failed { quest_id: "q_003", issue_day: 5, fail_day: 8, fine: 200 }`

### G6 — 아침 이벤트 수락률

> [!question] 이벤트 유형별 수락/거절 비율은?

- **측정** — `morning_event_resolved.choice` 분포. `morning_event_shown`의 유형별 등장 빈도와 교차하면 "자주 나오는데도 거절당하는 이벤트"를 식별할 수 있다.
- **구현** — ✅ Level 4 `morning_event_resolved` 정의됨.
- **왜 보는가** — 특정 이벤트의 거절률이 압도적으로 높으면 보상이 불충분하거나 조건이 불리한 것 -> 이벤트 밸런스 조정 근거.
- **예상 로그** — `morning_event_resolved { event_type: "guild_envoy", choice: "reject", day: 5 }`

### G16 — 퀘스트보드 던전 등급 선택 성향

> [!question] 퀘스트보드에서 어떤 등급의 던전을 주로 선택하는가? 고등급 도전 의지는?

- **측정** — `quest_board_confirmed.dungeon_grade` 분포. `day`와 교차하면 후반으로 갈수록 고등급 도전 비율이 오르는지 성장 곡선까지 볼 수 있다.
- **구현** — ✅ 이미 정의됨.
- **왜 보는가** — 저등급만 반복 선택하면 고등급 콘텐츠가 사실상 미사용 상태다. 보상 격차 또는 위험 인지 방식 개선이 필요하다.
- **예상 로그** — `quest_board_confirmed { dungeon_id: "cave_01", dungeon_grade: 1, day: 10 }`

### G25 — 의뢰판 새로고침 사용률

> [!question] 퀘스트보드를 열었을 때 새로고침하는 비율은? 초기 큐레이션이 만족스러운가?

- **측정** — `panel_opened(quest_board)` 대비 `btn_clicked(quest_board, refresh)` 비율. `day`와 교차하면 후반으로 갈수록 비용을 감당할 수 있어 비율이 오르는지 확인 가능하다.
- **구현** — ✅ 두 이벤트 모두 정의됨. 비율 계산은 대시보드에서 처리한다.
- **왜 보는가** — 새로고침 비율이 높으면 최초 제시된 던전 목록이 마음에 들지 않는다는 뜻 -> 큐레이션 알고리즘 개선.
- **예상 로그** — `btn_clicked { panel: "quest_board", button: "refresh", day: 12 }`

> [!tip] `refresh`는 횟수 소진 가드보다 **먼저** 발행한다
> G25가 재는 것은 "새로고침을 원했는가"다.

## 경제 & 성장

관련 도메인 문서: [[경제]] · [[유산_시스템]] · [[통찰_시스템]]

### G8 — 수색꾼 활용도

> [!question] 수색꾼을 얼마나 자주 파견하는가? 파견 화면까지 가서 실제로 보내는가?

- **측정** — `scout_sent` 일별 횟수 + `panel_opened(scout_dispatch)` 대비 `btn_clicked(scout_dispatch, send_scout)` 전환율.
- **구현** — ✅ 단, **`scout_result` 패널이 코드에 없으므로 "결과 확인율"은 측정 불가**다. 파견 화면 진입 대비 실제 파견 전환율로 대체한다.
- **왜 보는가** — 파견 화면까지 갔는데 보내지 않으면 비용이 부담되거나 효용을 모르는 것이다. 화면 진입 자체가 없으면 기능 인지 문제.
- **예상 로그** — `scout_sent { dungeon_id: "cave_01", armor_type: "heavy", day: 5 }`

### G10 — 골드·유산 흐름

> [!question] 어떤 경로로 골드/유산을 버는가? 어디에 가장 많이 쓰는가?

- **측정** — `gold_transaction`의 `source`별 earn/spend 금액 합계로 수입원·지출처 비중을, `legacy_transaction`의 `source`별 spend 비중으로 유산 사용처를 본다. `balance_after` 추적으로 유산이 쌓이기만 하는지 순환되는지 확인한다.
- **구현** — ✅ `EconomyManager.AddGold/SpendGold`에 reason 파라미터가 이미 있다. 한국어 reason을 `GetSourceAnalyticsName()`이 정규화한다.
- **왜 보는가** — 수입원과 지출처의 비중 파악이 경제 설계 검토의 핵심이다. "모험 보상보다 대여 수익 비중이 너무 낮다" 같은 불균형을 찾으면 보상 테이블을 조정한다.
- **예상 로그** — `gold_transaction { amount: 500, direction: "earn", source: "adventure_reward", day: 3 }`

### G20 — 유산 업그레이드 첫 구매 항목

> [!question] 가장 먼저 구매하는 업그레이드는? 게임에서 무엇이 가장 아쉬운가?

- **측정** — `legacy_upgraded`에서 `purchase_order = 1`인 이벤트만 필터링해 `upgrade_key` 분포를 본다.
- **구현** — ✅ 구현됨. `PlayerData.legacyUpgradePurchaseCount` 누적 카운터를 `LegacyManager.PurchaseUpgrade()`에서 증가시켜 전달한다. `category` 파라미터는 제외했다(카테고리 매핑이 UI 컨트롤러에만 있어 `upgrade_key`로 유도한다).
- **왜 보는가** — 첫 구매 항목 = 플레이 중 가장 먼저 아쉬움을 느끼는 부분. `StartingGold`에 집중되면 초반 경제가 너무 빡빡하다는 직접적 신호다.
- **예상 로그** — `legacy_upgraded { upgrade_key: "StartingGold", purchase_order: 1 }`

## 게임 흐름 & 유산

관련 도메인 문서: [[시간]] · [[튜토리얼]] · [[평판]]

### G2 — 평균 게임 시간

> [!question] 유저는 보통 몇 일째, 플레이 몇 분 만에 게임오버하는가?

- **측정** — `game_over.day` 분포로 "몇 일차에 주로 죽는가"를, `total_playtime_sec` 분포로 "실제 플레이 시간"을 **별도로** 확인한다.
- **구현** — ✅ `game_over.day`는 `TimeManager.CurrentDay`. `total_playtime_sec`은 `GameManager`에서 세션 시간 누적 추적이 필요하다.
- **왜 보는가** — "몇 일차에 주로 죽는가"가 난이도 곡선의 핵심 지표다. 12일 이전에 대부분 종료된다면 중반 난이도 조정이 필요하다.
- **예상 로그** — `game_over { day: 11, total_playtime_sec: 2700, reputation_level: "Silver", cause: "bankruptcy" }`

### G14 — 게임오버 후 재시작율

> [!question] 게임오버 후 새 게임을 시작하는 비율은? 유산 시스템이 재시작 동기를 주는가?

- **측정** — `game_over` 이후 세션에서 `game_start(is_new_game=false)` 비율. 원인별 분해는 [[퍼널]]의 퍼널 G가 담당한다.
- **구현** — ✅ 두 이벤트 모두 정의됨. 대시보드 세션 퍼널로 분석한다.
- **왜 보는가** — 유산 시스템의 재시작 동기 역할을 데이터로 검증한다. 재시작율이 낮으면 유산 업그레이드의 체감 효과가 약한 것이다.
- **예상 로그** — `game_start { is_new_game: false }` (앱 버전은 SDK가 `clientVersion`으로 자동 수집하므로 중복 파라미터 불필요)

### G15 — 핵심 루프 활성도

> [!question] 하루에 평균 몇 개의 모험을 보내는가? 일수가 늘어도 유지되는가?

- **측정** — `adventure_started`를 `day`로 그룹화해 일별 평균 횟수를 계산한다. 초반(1~5일)과 중반(6~15일)을 비교해 루프 지속성을 본다.
- **구현** — ✅ 공통 파라미터 `day`가 모든 이벤트에 포함된다.
- **왜 보는가** — 일별 모험 횟수가 중반부터 감소하면 무기 재고 부족 또는 골드 부족으로 루프가 막혔다는 신호다.
- **예상 로그** — `adventure_started { day: 8, dungeon_id: "forest_01", weapon_grade: 3 }`

### G18 — 평판 레벨 도달 분포

> [!question] 유저들이 보통 어느 평판 레벨에서 게임오버하는가?

- **측정** — `day_begin.reputation_level` 분포로 "주로 어느 레벨에서 플레이하는가", `game_over.reputation_level` 분포로 "어느 레벨에서 끝내는가"를 본다.
- **구현** — ✅ `ReputationLevel` enum 5단계(Bronze~Diamond)가 정의돼 있고 두 이벤트에 이미 포함된다.
- **왜 보는가** — 대부분이 Bronze에서 게임오버한다면 Silver 이상의 콘텐츠(빠른 스폰, 넓은 의뢰판)가 거의 소비되지 않는다는 신호다.
- **예상 로그** — `game_over { reputation_level: "Bronze", day: 8, cause: "bankruptcy" }`

### G27 — 튜토리얼 이탈 구간

> [!question] 신규 유저가 1일차 튜토리얼의 어느 단계에서 이탈하는가?

- **측정** — `tutorial_step.step`의 **유저별 최대 도달 단계** 분포 + [[퍼널]]의 퍼널 E.
- **구현** — ✅ `TutorialManager`의 `TutorialStep` enum(12단계)이 존재하고 `GameData.tutorialStep`으로 진행도가 저장된다. 단계 진입 시점에 발행한다.
- **왜 보는가** — 신규 유저 이탈은 대부분 첫 세션 튜토리얼 구간에서 발생하며 D1 리텐션과 직결된다. **우선순위가 가장 높은 목표다.**
- **예상 로그** — `tutorial_step { step: 4, step_name: "PrepEnter", day: 1 }`

## UI & UX

### G3 — UI 가시성

> [!question] 각 버튼이 처음 눌린 시점은? 끝까지 한 번도 안 눌린 버튼은?

- **측정** — 모든 `btn_clicked`에 `is_first_time: bool`을 포함한다. 대시보드에서 `is_first_time == true`만 조회하면 버튼 최초 클릭 시점(`day`) 분포를 볼 수 있다.
- **구현** — ✅ `AnalyticsManager`가 `{panel}_{button}` 키를 `PlayerPrefs`의 `HashSet<string>`(JSON 저장)으로 관리한다. Set에 없으면 `is_first_time = true`로 전송 후 추가.
- **왜 보는가** — 특정 버튼을 끝까지 한 번도 안 누른 유저 비율이 높으면 그 기능이 화면에서 보이지 않거나 존재를 모르는 것이다. 퍼널 C(통찰 탐색)와 결합하면 진입 장벽 구간을 특정할 수 있다.
- **예상 로그** — `btn_clicked { panel: "blacksmith", button: "tab_reroll", is_first_time: true, day: 7 }`

### G24 — 게임 속도(배속) 설정 분포

> [!question] 유저들이 주로 몇 배속으로 플레이하는가?

- **측정** — `speed_changed.speed_multiplier` 분포. `day`/`phase`와 교차하면 특정 시간대에만 속도를 높이는 패턴도 파악된다.
- **구현** — ✅ `TimeManager.SetTimeScale()` 호출 시 발행. Level 1에 정의됨.
- **왜 보는가** — 항상 최대 배속이라면 기본 배속이 너무 느린 것 -> 기본값 상향 또는 자동 배속 검토.
- **예상 로그** — `speed_changed { speed_multiplier: 4.0, day: 3 }`
