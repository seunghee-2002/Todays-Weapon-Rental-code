# 다국어_도입전략

> [!abstract] 한 줄 요약
> 한국어 전용 게임에 **한국어(기본)/영어/일본어/중국어(간체)** 4개 언어를 Unity Localization 패키지로 도입하는 전략. TranslateView(언어 선택 패널) + 확인 팝업 + PlayerPrefs 영속화가 1차 목표이며, 기존 문자열 ~2,300개는 6개 Phase로 나눠 단계 이관한다.

> [!important] 사전 결정 사항 (2026-08-01 확정)
> - **번역 초안**: Claude가 en/ja/zh-Hans 작성 -> 사용자 검수
> - **ja/zh 폰트**: 사용자가 직접 준비한 폰트 사용 (라이선스 확인 포함). 폰트 파일 제공 시점에 SDF 생성·폴백 연결
> - 이 문서는 전략만 담는다. 구현은 이후 Phase 단위로 별도 진행

## 1. 현재 상태 진단 (2026-08-01 탐색 결과)

### 이미 깔려 있는 것 (재사용)

- `com.unity.localization` **1.5.12 설치 완료** (`Packages/manifest.json`), Addressables 1.25.0 종속 설치 + `Assets/AddressableAssetsData/`에 Localization 전용 그룹 자동 생성 완료
- `Assets/_Projects/Data/Localization/`: `Localization Settings.asset`, 로케일 ko-KR/en 2개, String Table `AppName` 1개(안드로이드 앱 표시명 1엔트리)
- 코드에서 `UnityEngine.Localization` 참조 **0건** — 게임 문자열은 전부 미적용 상태
- 시작 셀렉터: CommandLine -> System -> Specific(en). **PlayerPrefLocaleSelector 없음** (영속화 미구성)
- String/Asset Database 모두 **UseFallback: 0** (폴백 꺼짐)

### 문자열 인벤토리 (총 ~2,300개)

| 위치 | 규모 | 비고 |
|---|---|---|
| 코드 (비 Editor) | ~850줄 / ~100파일 | 허브: `UITranslator.cs` 133개(enum 라벨), 토스트/팝업 깔때기 `UIPopupController` ~40 콜사이트 |
| 프리팹/씬 구움 텍스트 | 391줄 / 81프리팹 + 씬 18줄 | `m_text:`에 한글 직접 입력된 고정 라벨 |
| SO 데이터 | ~1,100줄 | WeaponData·WeeklyQuestData(최대 409줄)·DialogueData 등 13종 + Config SO 서사 텍스트(SeerConfig 등) |
| 법적 문서 | 2파일 | `Data/Text/PrivacyPolicy.txt`, `TermsOfService.txt` (TextAsset) |

> [!danger] 최대 리스크 = 폰트
> 전 UI가 `Maplestory Light SDF`(static 2048², 한글+ASCII ~11.3k 글리프, 폴백 없음) 단일 참조(82파일/1,109참조). 가나/한자 글리프가 전무해 **ja/zh는 현재 렌더링 자체가 불가능**. `KERISKEDU_B/Line SDF`(74MB)는 미사용 상태.

**한국어 종속 코드:** `UITranslator.ObjectParticle`(을/를 받침 판정) + 콜사이트 ~15곳의 `을(를)`/`이(가)` 병기, `FormatDuration`("N시간N분").

## 2. 권장 아키텍처 요약 (결정 테이블)

인디 규모에 맞춘 결정. 핵심 원칙: **"폴백을 먼저 켜서 어느 단계에서 멈춰도 미번역은 한국어로 표시"** — 마이그레이션 전 기간 게임이 깨지지 않는다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 영속화 | 내장 `PlayerPrefLocaleSelector` (키 `selected-locale`) | 시작 복원 + 변경 시 기록을 패키지가 전담 — 커스텀 저장 코드 0줄. 계정 초기화(`CloudSaveManager.WipeDataAsync`)는 개별 키만 지우므로 자동 생존 |
| 시작 복원 | 셀렉터가 초기화 시 자동 수행 | 별도 부트스트랩 코드 불필요 |
| 매니저 | 얇은 `LocalizationManager : BaseManager<T>` 신설 (DDOL, MainMenuScene) | 로케일 목록/변경/이벤트 릴레이/폰트 폴백 스왑 4책임만 |
| TranslateView | 컨트롤러 없음, `BGMChangeView` 구조 복제 | 설정 계열 뷰가 인프라 매니저(SoundManager) 직접 호출하는 선례 확립됨. 패스스루 컨트롤러는 Simplicity First 위반 |
| String Table | 6개 분할 (UI 3 + Data 2 + Dialogue 1) | 도입 페이즈 경계 = 테이블 경계 |
| 폴백 | String Database UseFallback 켜기 + en/ja/zh 로케일에 Fallback 메타데이터 -> ko-KR | 단계적 출시의 핵심 장치 |
| 폰트 | Maplestory 유지 + ja/zh 폰트를 **폴백 체인**으로 추가, 로케일 변경 시 폴백 순서만 스왑 | 프리팹 1,109개 참조 무수정 |
| UITranslator | public API 유지, 내부만 테이블 조회로 교체 | 콜사이트 ~100파일 무수정 |
| SO 데이터 | ID 키 조회 + **SO 한국어 원문이 곧 폴백** (ko 데이터 테이블 안 만듦) | 한국어 이중 관리 제거. 마지막 페이즈로 연기 |
| Asset Table | **당장 불필요** | 폰트는 폴백 체인 방식이라 테이블 스왑 불필요. 법적 문서 TextAsset만 후순위 후보 |
| 초기화 | `m_InitializeSynchronously: 0` 유지 (비동기) | 동기 초기화는 앱 기동 지연. 코드 조회는 내부 WaitForCompletion로 커버(로컬 콘텐츠라 수 ms) |

## 3. 전체 적용 전략 — 6 Phase 로드맵 (각 단계 단독 출시 가능)

```
Phase 0  에디터 기반 작업 (코드 0줄)         -> 검증: ja/zh 로케일 존재, 폴백 동작            [완료]
Phase 1  언어 전환 골격 (1차 목표)           -> 검증: 전환·저장·재시작 복원·확인 팝업 동작     [완료]
Phase 2  UITranslator 내부 교체 (enum 133개) -> 검증: 등급/무기유형 라벨이 언어 따라 변경      [완료]
Phase 3  화면(프리팹+씬+코드) 단위 이관       -> 검증: 그 화면에 한국어가 하나도 안 남았는지    [완료 2026-08-03]
Phase 5  SO 데이터 (1,002줄)                -> 검증: 무기/퀘스트/대사 전환 확인              [완료 2026-08-03]
Phase 6  폴리시 (법적 문서, 닉네임 정규식, 미사용 폰트 정리 등)                              [진행 중]
```

> [!success] Phase 3 완료 (2026-08-03)
> 프리팹/씬 부착 192건 · 코드 문구 전량 키 조회 전환 · 테이블 키 578 -> 1,105개.
> 「그 화면에 한국어 0건」을 **스크립트로 증명**하는 방식으로 바꿨다 — [[다국어_감사대장]] 참고.
> 진행 내역·검수 요청·남은 것은 [[다국어_진행상황]].

> [!important] Phase 3·4를 합쳤다 (2026-08-02 개정)
> 원래는 **Phase 3 = 프리팹 고정 라벨 / Phase 4 = 코드 문자열**로 나눠 두 번에 걸쳐 훑을 계획이었다. 실제로 해보니 이 분할이 잘못됐다.
>
> - 한 화면이 **반쪽만 번역된 채** 남는다. 옵션·메인메뉴·인벤토리를 "완료"로 처리했는데 같은 화면 코드에 한국어가 44건 남아 있었다.
> - 확인할 때 **"이게 왜 한국어지?"를 프리팹 탓인지 코드 탓인지 매번 구분**해야 한다. 테스트가 불가능에 가깝다.
> - 실제로 `WeaponShopView`의 새로고침 비용을 "코드니까 Phase 4"로 미뤄 놓고 화면을 완료로 보고했다.
>
> **개정: 화면(프리팹) 하나를 잡으면 그 화면이 쓰는 모든 TMP를 한 번에 끝낸다.** 구움 라벨(`LocalizeStringEvent` 부착)과 코드 구동 문구(키 조회 교체)를 같은 배치에서 처리하고, **그 화면에 한국어가 0건이어야 완료**다. SO 데이터(Phase 5)와 법적 문서(Phase 6)만 성격이 달라 뒤로 남긴다.

### Phase 0 — 에디터 기반 작업 (코드 0줄)

1. Locale Generator(`Window > Asset Management > Localization Tables`)로 **Japanese (ja)**, **Chinese (Simplified) (zh-Hans)** 로케일 생성 -> `Assets/_Projects/Data/Localization/` (Addressables `Localization-Locales` 그룹 자동 등록)
2. `Localization Settings.asset` 시작 셀렉터 재구성: **CommandLine -> PlayerPrefLocaleSelector(`selected-locale`) -> System -> Specific(en)**
   - Specific(en) 유지: 미지원 시스템 언어(독일어 등) 기기의 국제 폴백. zh-CN 기기는 SystemLocaleSelector가 CultureInfo 부모 체인으로 zh-Hans에 매칭
3. String Database **Use Fallback 체크** + en/ja/zh-Hans 로케일 자산에 Metadata -> Fallback Locale = Korean(ko-KR)
4. 폰트: 사용자 제공 ja/zh 폰트 임포트 -> SDF 생성 -> 폴백 연결 (10절. **폰트 파일이 준비 안 됐으면 이 항목만 뒤로 미루고 진행 가능** — ja/zh 선택 시 두부(□) 표시 감수)
5. Addressables 설정 "Build Addressables content on Player Build" 활성화 (안드로이드 빌드 원클릭 유지)
6. TMP 문자 범위 규칙 개정(`CLAUDE.md` + [[Development]]): "코드/프리팹의 한국어 원문은 기존 범위 유지, **번역 테이블 텍스트는 해당 로케일 폰트 아틀라스가 커버하는 범위 허용**, 릴리즈 전 번역 텍스트 기반 아틀라스 재생성 필수"

### Phase 1 — 언어 전환 골격 (1차 목표)

- `LocalizationManager.cs` 신설 + MainMenuScene 배치
- `TranslateView.cs` + `TranslateLanguageItem.cs` + 프리팹 2종 + UIManager `panelPrefabs` 등록
- `OptionPopupView`(인게임) / `MainMenuOptionView`(메인메뉴) 양쪽에 `languageButton` 추가
- `UI_Common` 테이블 생성 + 초기 키 10개 미만(패널 제목, 확인 문구, 공용 단어) 4개 언어 입력
- `AppName` 테이블에 ja/zh 엔트리 추가
- **완료 기준: 언어를 바꿔도 대부분 화면은 한국어(폴백)지만, 전환·저장·복원·폰트가 전부 동작**

### Phase 2 — UITranslator 내부 교체

- API 표면 유지, switch 문 내부만 `GetLocalizedString("UI_Common", $"Grade_{grade}")` 조회로 교체 -> 콜사이트 ~100파일 무수정
- enum 라벨 133개 x 4개 언어 번역 입력
- 주의: UITranslator 경유 텍스트는 로케일 변경 시 자동 갱신 안 됨 -> 변경 진입점이 설정 패널뿐이고 패널은 Open 시 재구성되므로 대부분 자연 해소. 상시 HUD(TopBar/BottomBar)만 `OnLocaleChanged` 구독 갱신 추가

### Phase 3 — 화면(프리팹) 단위 이관

**한 화면을 잡으면 그 화면이 쓰는 모든 TMP를 끝낸다.** 구움 라벨과 코드 구동 문구를 나누지 않는다.

작업 순서 (화면 하나당):

1. **전수 추출** — 해당 프리팹/씬의 `m_text` 전부 (YAML 줄바꿈 접힘 주의) + 그 화면의 View/Controller/ListItem 코드의 한국어 리터럴 전부
2. **분류** — 직렬화 필드 참조로 판별한다
   - 코드가 안 건드림 -> `LocalizeStringEvent` 부착 (`UI_Screens`)
   - 코드가 `text`에 씀 -> **부착 금지**, 코드에서 키 조회로 교체
   - **같은 화면인데 둘이 섞여 있는 게 정상이다. 둘 다 이번 배치에서 처리한다.**
3. **완료 기준** — 그 화면의 프리팹·코드 양쪽에서 **한국어 검색 결과가 0건**
4. 예외로 남기는 것: SO 데이터(Phase 5), 법적 문서 TextAsset(Phase 6), 유저 데이터(닉네임·ID·숫자)

배치 순서: 옵션 2종+TranslateView -> 메인메뉴 -> 인게임 상시 HUD -> 나머지 패널 (회당 1~2화면씩 나눠 출시 가능)

**공통 인프라** (여러 화면이 함께 쓰는 것)는 화면 배치와 별개로 한 번에 처리한다:
- `UIPopupController`의 토스트/확인 팝업 문구 (~40 콜사이트) -> `UI_Messages` 테이블
- `{0}` 포맷 -> Smart String 이름형 인자 (9절), 조사(을/를) 처리 (9절)

### Phase 5 — SO 데이터 (~1,100줄)

- `DataLocalizer` 정적 헬퍼: 키 `Weapon_{id}_Name` 조회, **현재 로케일이 ko이거나 엔트리 없으면 SO 한국어 필드 그대로 반환** -> ko 데이터 테이블을 아예 만들지 않음 (SO 원문 = 한국어 소스, 이중 관리 제거)
- SO에 `public string DisplayName => DataLocalizer.WeaponName(this);` 프로퍼티를 얹어 콜사이트 치환을 기계적으로
- 툴링: 기존 CSV 툴(`Scripts/Editor/`)에 "Localization Export" 탭 추가 — 13종 SO + Config SO 서사 텍스트를 순회해 `Key, ko(원문 참고), en, ja, zh-Hans` CSV 생성 -> 번역 후 Localization 패키지 내장 CSV 확장으로 임포트
- LocalizedString 필드 방식(SO 전 자산 수정 + CSV 툴 직렬화 전면 개조 필요)은 기각

### Phase 6 — 폴리시 (선택)

- 법적 문서: `LocalizedAsset<TextAsset>` Asset Table 전환 (이때가 Asset Table 첫 도입 시점)
- `NicknameConfig.allowedPattern` `^[가-힣a-zA-Z0-9_]+$` **유지** — ja/zh 문자 허용으로 한번 넓혔다가 10절 Static 재베이크와 양립 불가라 철회했다(경위는 [[다국어_진행상황]] Phase 6). 금칙어 다국어화만 남음
- 미사용 KERISKEDU 폰트 74MB 정리 (별건)

## 4. 프로젝트 구조

### 폴더 구조 (기존 위치 유지)

```

├─ Korean (South Korea) (ko-KR).asset   (기존)
├─ English (en).asset                   (기존 — 폴백 메타데이터 추가)
├─ Japanese (ja).asset                  (신규)
├─ Chinese (Simplified) (zh-Hans).asset (신규)
├─ AppName*.asset                       (기존 — ja/zh 엔트리 추가)
└─ Tables/                              (신규 — 테이블 컬렉션은 하위 폴더로 정리)
   ├─ UI_Common/   ├─ UI_Screens/   ├─ UI_Messages/
   ├─ Data_Items/  ├─ Data_World/   └─ Dialogue/

Assets/_Projects/Scripts/Systems/LocalizationManager.cs        (신규)
Assets/_Projects/Scripts/UI/Views/TranslateView.cs             (신규)
Assets/_Projects/Scripts/UI/ListItems/TranslateLanguageItem.cs (신규)

Assets/_Projects/Prefabs/UI/ListItem/TranslateLanguageItem.prefab (신규)
```

### String Table 구성 (6개 + 기존 AppName)

하나로 합치면 편집·CSV 왕복·단계별 마이그레이션이 전부 괴롭고, 잘게 쪼개면 관리 비용만 는다. **도입 페이즈 경계와 테이블 경계를 일치**시킨 6분할:

| 테이블 | 내용 | 규모 | 프리로드 | 페이즈 |
|---|---|---|---|---|
| `UI_Common` | 공용 단어(확인/취소/닫기), enum 라벨 전체, 시간·단위 포맷, 특성 효과 포맷 | ~200 | O | 1~2 |
| `UI_Screens` | 화면별 고정 라벨 (프리팹 391 + 씬 18) | ~450 | O | 3 |
| `UI_Messages` | 토스트/팝업 문장, 뷰 코드 문장 | ~500 | O | 4 |
| `Data_Items` | 무기/재료/액티브아이템 이름·설명 | ~300 | O | 5 |
| `Data_World` | 던전/던전이벤트/주간퀘스트/방문자이벤트/모험가 + Config SO 서사 | ~600 | X (지연) | 5 |
| `Dialogue` | DialogueData 대사·화자, 대장장이 인사 | ~300 | X (지연) | 5 |

- 프리로드는 테이블별 Preload 토글. PreloadBehavior 1(선택 로케일만)이라 선택 언어분 수백 KB만 메모리 상주 — 부담 무시 가능
- `Data_World`/`Dialogue`는 인게임 진입 후 첫 접근 시 동기 로드(`WaitForCompletion`) — 로컬 Addressables라 수 ms

### Asset Table 필요 여부

**당장 불필요.** 폰트는 폴백 체인 방식(10절)이라 로케일별 폰트 테이블 스왑이 필요 없고, 이미지에 언어별 차이가 없다. 유일한 후보는 법적 문서 TextAsset — Phase 6에서 도입.

## 5. String Key 설계

**기능(도메인) 기반을 기본으로 하되, 화면 고유 라벨만 화면 접두어** — 테이블별로 규칙을 달리하는 하이브리드. 순수 화면 기반은 같은 문장("골드가 부족합니다"가 여러 화면)이 화면마다 중복 키가 되는 문제가 있고, 순수 기능 기반은 화면 고유 라벨에서 오히려 어색하다.

형식: **언더스코어 구분 PascalCase**. 점(`.`)은 Smart String 셀렉터 연산자와 겹치므로 금지.

| 테이블 | 형식 | 예시 |
|---|---|---|
| UI_Common (enum) | `{EnumType}_{Value}` — 코드에서 `$"Grade_{grade}"` 자동 조합 | `Grade_Common`, `WeaponType_Sword`, `TraitType_Lucky`, `Common_Unknown` |
| UI_Common (공용) | `Common_{용도}` | `Common_Confirm`, `Common_Cancel`, `Common_DurationHM` |
| UI_Screens | `{View명에서 View 제거}_{요소}` | `OptionPopup_Title`, `Translate_Title`, `QuestBoard_RefreshButton` |
| UI_Messages | `{도메인}_{사건}` | `Economy_NotEnoughGold`, `Save_Completed`, `Quest_SelectDungeon` |
| Data_* | `{SO종류}_{id}_{필드}` | `Weapon_W001_Name`, `Weapon_W001_Desc`, `Quest_WQ003_Title` |
| Dialogue | `{SO종류}_{id}_{라인번호}` | `Dialogue_D012_0`, `Blacksmith_B001_Greeting_2` |

- Smart String 인자는 순서형 `{0}` 대신 **이름형** (`{value}`, `{days}`, `{name}`) — 어순이 다른 언어에서 번역가가 위치를 옮길 수 있고 CSV에서 의미가 읽힘
- enum 키는 코드 조합이 전제이므로 **enum 멤버명 변경 = 키 변경**임을 규칙으로 명시

## 6. TranslateView 설계

### 컨트롤러 여부: 없음

[[UI_구조]]의 View -> Controller 규칙은 "도메인 매니저는 반드시 Controller 경유"인데, LocalizationManager는 SoundManager와 같은 **인프라 계층**이고, 설정 계열 뷰(`BGMChangeView`, `OptionPopupView`)가 SoundManager/GameManager를 직접 호출하는 선례가 확립돼 있다. 패스스루 메서드 2개짜리 컨트롤러는 Simplicity First 위반.

### UI 요소 목록

| 요소 | 종류 | 비고 |
|---|---|---|
| 패널 타이틀 | TextMeshProUGUI | `LocalizeStringEvent`(`Translate_Title`) |
| 언어 행 x4 | 런타임 생성 리스트 | `TranslateLanguageItem` 프리팹 (BGMChangeItem 선례) |
| ├ 언어명 라벨 | TextMeshProUGUI | **항상 원어 고정 표기**: 한국어 / English / 日本語 / 简体中文 — 번역하지 않음(자기 언어를 못 읽는 유저 배려). 폴백 폰트 체인 덕에 ko 상태에서도 한자·가나 표시됨 |
| └ 선택 표시 | GameObject (체크/하이라이트) | 현재 로케일 행만 활성 |
| 닫기 버튼 | Button | |
| 오버레이/ESC | BaseView 표준 | `pauseTimeOnOpen=true, isCanClickOverlay=true, canEscape=true` |

### 동작 흐름

```
행 탭 -> 현재 언어와 같으면 무시
-> UIPopupController.ShowPopup("언어를 '日本語'(으)로 변경하시겠습니까?", onConfirm, onCancel)
-> 확인 시 LocalizationManager.ChangeLocale(locale)
-> PlayerPrefLocaleSelector가 selected-locale 키 자동 기록 (+PlayerPrefs.Save())
-> OnLocaleChanged 수신 -> 선택 표시 갱신 (LocalizeStringEvent 붙은 라벨은 자동 갱신)
```

- 확인 문구는 `UI_Common`의 `Translate_ConfirmChange`(Smart String, `{name}` = 대상 언어 원어명)를 **현재 언어로** 표시. 대상 언어로 띄우는 방식은 비선택 로케일 테이블 추가 로드가 필요한데 원어명이 이미 문구에 있으므로 과투자
- `OnEscapeClicked` 오버라이드 금지 — `CloseTopPanel`이 `Close()`까지 처리하므로 오버라이드하면 이중 Close (BGMChangeView 주석의 확립된 규칙)

### 진입점

`OptionPopupView`(인게임) / `MainMenuOptionView`(메인메뉴) 양쪽에 `languageButton` -> `UIManager.Instance?.OpenPanel<TranslateView>()`. UIManager가 DDOL이므로 MainMenuScene 인스펙터의 `panelPrefabs` 등록 한 번으로 양 씬 커버.

## 7. 코드 구조

### LocalizationManager (신규, `Scripts/Systems/LocalizationManager.cs`)

필요하다 — 단 4가지 책임만: (1) 지원 로케일 고정 순서(ko->en->ja->zh) 제공, (2) `ChangeLocale` + 직후 `PlayerPrefs.Save()`(프로젝트 관례 + 안드로이드 강제 종료 대비), (3) 프로젝트 스타일 `event Action<Locale> OnLocaleChanged` 릴레이, (4) 로케일별 폰트 폴백 순서 스왑.

```csharp
public class LocalizationManager : BaseManager<LocalizationManager>
{
    public event Action<Locale> OnLocaleChanged;
    public Locale CurrentLocale => LocalizationSettings.SelectedLocale;
    public IReadOnlyList<Locale> SupportedLocales { get; }   // 고정 순서 정렬

    [Header("폰트 폴백")]
    [SerializeField] private TMP_FontAsset baseFont;     // Maplestory Light SDF
    [SerializeField] private TMP_FontAsset fallbackJP;   // 사용자 제공 ja 폰트 SDF
    [SerializeField] private TMP_FontAsset fallbackSC;   // 사용자 제공 zh 폰트 SDF

    protected override void Awake()
    {
        base.Awake();
        if (Instance != this) return;
        DontDestroyOnLoad(gameObject);                        // SoundManager와 동일 패턴
        var _ = LocalizationSettings.InitializationOperation; // 초기화 조기 킥(셀렉터가 저장 로케일 복원)
        LocalizationSettings.SelectedLocaleChanged += HandleLocaleChanged;
    }
    // OnDestroy: 구독 해제

    public void ChangeLocale(Locale locale)
    {
        LocalizationSettings.SelectedLocale = locale;  // PlayerPrefLocaleSelector가 자동 기록
        PlayerPrefs.Save();
    }

    private void HandleLocaleChanged(Locale locale)
    {
        ApplyFontFallbackOrder(locale);   // ja -> [JP, SC], zh-Hans -> [SC, JP] (10절)
        OnLocaleChanged?.Invoke(locale);
    }

    public static string GetNativeName(Locale locale)
    { /* ko->한국어, en->English, ja->日本語, zh-Hans->简体中文 고정 맵, 미등록 시 CultureInfo.NativeName */ }
}
```

- **배치:** MainMenuScene 매니저 루트(SoundManager 옆). `GameManager.InitializeManagers()`(인게임 전용) 등록 불필요 — GameData와 무관한 앱 설정이므로 씬 오브젝트 DDOL로 충분
- **PlayerPrefs 수동 구현은 하지 않는다** — 셀렉터와 이중 기록 위험만 추가. "PlayerPrefs 저장" 요구는 셀렉터가 PlayerPrefs를 쓰므로 충족
- **초기화 타이밍:** `m_InitializeSynchronously: 0` 유지. LocalizeStringEvent는 초기화 완료 시 자동 갱신되고, 코드 조회는 내부 WaitForCompletion — 로컬 콘텐츠라 최악 수십 ms 1회. MainMenu는 UGS 대기(최대 10초)가 이미 있어 체감 없음

### 게임 시작 시 언어 복원 흐름 (코드 0줄)

```
앱 시작 -> LocalizationSettings 초기화 (첫 접근 시)
-> 셀렉터 순회: CommandLine(-language=) -> PlayerPref(selected-locale) -> System -> Specific(en)
-> 저장된 로케일 있으면 즉시 복원, 첫 실행이면 기기 언어 매칭(zh-CN 기기 -> zh-Hans)
```

## 8. 기존 UI 마이그레이션 전략 (수백 개 텍스트 효율 처리)

### 순서 (Phase 3 세부)

1. **화면 하나를 잡고 그 화면의 프리팹 라벨 + 코드 문구를 같이 끝낸다.** 순서: 옵션/TranslateView -> 메인메뉴 -> 상시 HUD -> 나머지 화면
2. **공통 깔때기는 별도 배치** — `UIPopupController` 키 오버로드(~40 콜사이트 커버)는 화면 단위와 무관하게 한 번에
3. 회당 1~2화면씩. 폴백 덕에 부분 적용 상태로 출시 가능

### 효율화 도구

- 프리팹 구움 텍스트 391개의 키·원문 추출은 **스크립트로 자동화** — `.prefab` YAML의 `m_text:`를 파싱해 `UI_Screens` 키 초안 CSV 생성 (한글이 `\uXXXX` 이스케이프로 저장되므로 파서에서 디코딩 필요 — 수동 grep은 누락됨)
- 번역 입력은 Localization 패키지 내장 CSV Extension으로 왕복 (기존 CSV 툴 문화와 동일한 워크플로)

### 실수하기 쉬운 부분

> [!warning] 체크리스트
> - **`LocalizeStringEvent`와 코드 `text =` 대입 충돌** — 같은 텍스트에 둘 다 걸리면 로케일 변경/활성화 시점에 서로 덮어씀. 코드가 쓰는 텍스트는 반드시 코드 경로로만
> - 프리팹 중첩(Nested Prefab) 오버라이드 — 부모 프리팹에 컴포넌트를 달았는데 인스턴스에 `m_text` 오버라이드가 남아 있으면 겉보기 정상, 로케일 변경 시만 갱신 안 되는 유령 버그
> - `UITranslator` 경유 문자열은 로케일 변경 자동 갱신이 없음 — 상시 HUD만 `OnLocaleChanged` 구독 추가
> - 로케일 변경 시 열려 있던 패널 — 변경 진입점이 설정 패널뿐이고 패널은 Open 시 재구성이므로 대부분 자연 해소. 예외만 개별 대응
> - 문자열 연결(`+`)로 조립된 문장(`UIPopupController`의 골드 부족 문구 등) — 조각별 번역 금지, 문장 전체를 한 키로 재작성

## 9. 동적 문자열 처리 (Smart String)

테이블 엔트리에 **Smart 체크**를 켜고 이름형 인자를 사용한다. 호출부는 인자 딕셔너리(또는 익명 객체)를 넘긴다.

| 한국어 원문 | 키/엔트리 예시 | 비고 |
|---|---|---|
| `{0}명` | ko `{count}명` / en `{count} {count:plural:person\|people}` | PluralLocalizationFormatter가 이미 세팅에 등록돼 있음. ja/zh는 복수형 없음 — `{count}名` / `{count}人` |
| `남은 시간 {0}` | ko `남은 시간 {time}` / en `Time left: {time}` | |
| `공격력 +{0}` | ko `공격력 +{value}` / en `ATK +{value}` | |
| `{PlayerName}님 환영합니다` | ko `{playerName}님 환영합니다` / en `Welcome, {playerName}!` | 어순 이동의 전형 예 — 이름형 인자라 번역가가 자유 배치 |
| `생존: {0}일` (GameOverPopupView) | ko `생존: {days}일` / en `Survived {days} {days:plural:day\|days}` | 기존 유일한 `{0}` 클러스터 |
| `N시간N분` (`FormatDuration`) | `Common_Duration_H` / `_M` / `_HM` 3키 | 시간/분 유무 분기는 C#에 유지 |

**호출 예:**

```csharp
string msg = LocalizationSettings.StringDatabase.GetLocalizedString(
    "UI_Messages", "Adventure_Survived",
    arguments: new object[] { new Dictionary<string, object> { { "days", days } } });
```

### 한국어 조사(을/를, 이/가) — 콜사이트 ~15곳

1. **1순위: 조사가 필요 없게 문장 재작성** — `"[{item}] 획득!"` 식. 번역 품질도 좋아짐
2. **2순위: ko 엔트리에 병기 표기** `"을(를)"` — 현 코드의 안전 폴백과 동일
3. 커스텀 SmartFormat 포매터(받침 판정 ~50줄)는 가능하지만 15곳을 위한 과투자 — 폴리시 단계 선택지로만 보류

- `UITranslator.ObjectParticle`은 마이그레이션 완료 시 자연 소멸

### 리치 텍스트 색상 태그

번역문 안에 태그를 그대로 두되 동적 색상은 인자로 주입: ko `"성공률 {rate}% <color={green}>({sign}{bonus}%)</color>"` — hex는 기존 ColorManager 값. 번역 CSV에 "태그/중괄호 훼손 금지" 주의 컬럼 명시, 임포트 후 `{`·`<color` 짝 검증(선택).

## 10. 폰트 전략 (사용자 제공 폰트 전제)

**구조: Maplestory Light SDF를 배정 폰트로 유지 + ja/zh 폰트를 폴백 체인으로 추가 + 로케일 변경 시 폴백 순서만 스왑.**

- 프리팹 1,109개 폰트 참조를 **한 개도 수정하지 않는 것**이 이 구조의 최대 가치
- Asset Table로 폰트 자체를 스왑하는 방식은 전 텍스트의 머티리얼 프리셋까지 흔들려 기각

**절차 (사용자 폰트 파일 제공 시):**

1. ja/zh 폰트 임포트 (라이선스 확인은 사용자 책임. 필요 글리프: ja = 가나 + 상용한자 ~2,100자 이상, zh-Hans = 통용규범한자 ~3,500자 이상 커버 확인)
2. Font Asset Creator로 SDF 생성 — **개발 중에는 Dynamic 모드**(번역 작업 비블로킹), **릴리즈 전 번역 CSV에서 추출한 실사용 문자만으로 Static 재베이크** (Font Asset Creator "Characters from File"). 아틀라스 2048x2048에서 시작(실사용 ja ~1.5k / zh ~2k 글리프면 수용), 부족 시 4096x2048 (Alpha8 기준 4->8MB — 모바일 허용 범위)
    - **용량 이득은 여기서 나온다:** Static으로 구우면 `m_SourceFontFile` 참조를 비울 수 있어 소스 TTF가 빌드에서 빠진다 — `GenJyuuGothic-Bold.ttf` 11.0MB + `ZCOOLQingKeHuangYou-Regular.ttf` 7.9MB = **약 19MB**. `Maplestory Light SDF`가 이미 그 상태(`m_SourceFontFile: {fileID: 0}`)다. 반대로 Dynamic을 유지하면 런타임 글리프 생성을 위해 TTF를 계속 실어야 한다
    - **전제: 닉네임에 가나·한자를 허용하지 않는다.** 닉네임은 임의 입력이라 실사용 문자를 미리 뽑을 수 없어, 재베이크하는 순간 아틀라스에 없는 글자가 두부가 된다. 그래서 `allowedPattern`을 한글/영문/숫자/`_`로 되돌렸다(Phase 6)
    - 재베이크 전까지는 Dynamic이므로 **번역 텍스트 실사용 문자가 아틀라스에 미리 구워져 있지 않다** — ja 1,130자 / zh-Hans 1,546자 중 상당수가 플레이 중 생성된다. 재베이크가 이것도 같이 해소한다
3. `Maplestory Light SDF`의 Fallback Font Assets에 [JP, SC] 추가 + TMP Settings 글로벌 폴백에도 동일(안전망). 이것만으로 ko 화면의 "日本語/简体中文" 라벨까지 즉시 표시
4. **Han unification 대응:** ja/zh가 공유하는 한자 코드포인트는 폴백 1순위 폰트의 자형으로 그려짐 -> `LocalizationManager.ApplyFontFallbackOrder`가 로케일 변경 시 `fallbackFontAssetTable` 순서를 ja -> [JP, SC] / zh-Hans -> [SC, JP]로 재배열 (코드 ~10줄)

> [!note] 주의
> 폰트별 baseline/line height 차이로 ja/zh에서 줄 간격이 미세하게 달라질 수 있음 — Face Info의 Line Height 보정으로 맞춤. 릴리즈 전 QA 항목에 "긴 문장 UI(퀘스트 설명 등) 4개 언어 오버플로 확인" 포함 (번역문 길이: zh는 짧아지고 en은 30~40% 길어지는 경향).

## 11. 성능 (모바일)

- **메모리:** 선택 로케일 텍스트 수백 KB + 폰트 아틀라스(static 4~8MB/언어, 해당 로케일 폴백만 로드됨) — 부담 없음
- **조회 비용:** 프리로드된 테이블의 `GetLocalizedString`은 사실상 딕셔너리 조회. `Update()`에서 매 프레임 호출만 금지(기존 UI가 이벤트 기반 갱신이라 해당 없음)
- **`WaitForCompletion`:** 안드로이드 로컬 콘텐츠에서 안전(WebGL 아님). 지연 테이블 첫 접근 시 수 ms 1회
- **로케일 전환:** 신규 로케일 테이블 비동기 로드 1회 — 이 규모에선 로딩 화면 불필요
- **Addressables 빌드:** "Build Addressables content on Player Build" 켜서 원클릭 유지. **이 설정을 빼먹으면 에디터에선 정상인데 디바이스에서 테이블이 통째로 실종** — 최대 함정. 에디터 Play Mode는 Use Asset Database 스크립트라 별도 빌드 불필요
