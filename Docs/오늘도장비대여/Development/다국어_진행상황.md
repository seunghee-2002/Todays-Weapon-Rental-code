> [!abstract] 한 줄 요약
> **어느 화면에 어떤 텍스트가 남았고 어디까지 했는지**를 추적하는 작업 대장. **Phase 3(프리팹·씬·코드)과 Phase 5(SO 데이터)는 2026-08-03 완료**했고, 남은 것은 Phase 6(약관 번역·금칙어 다국어화·폰트 재베이크)이다. 전략·설계는 [[다국어_도입전략]], 도구는 [[다국어_감사대장]], 작업 절차·함정은 `/localize` 스킬에 있다.

> [!tip] 테스트 단축키 (에디터/개발 빌드 전용)
> - **F11** — 다음 언어로 순환 (`ko-KR > en > ja > zh-Hans`). 부착된 라벨은 즉시 바뀐다. 우측에 `Locale: xx` 토스트 표시

> [!important] 갱신 방법 (2026-08-02 개정)
> 수치는 **감사 스크립트**로 뽑는다. 손으로 세지 않는다. 도구 설명은 [[다국어_감사대장]].

**S14에서 잡아낸 것 - `SeerConfig`는 「중첩 없는 SO 직속 리스트」가 아니었다**

착수 문서에는 `SeerConfig` 163건이 *SO 직속 리스트(중첩 없음)라 지금 파서로 이미 잘 나온다*고 적혀 있었다. **틀렸다.** 163건 중 **100건**이 `AbstractLuckLines` 구조체 5개(`descGreat`/`descGood`/`descNormal`/`descHarsh`/`descGrim`) 안의 `bad`/`minor`/`good`/`great` 리스트에 들어 있다. 평면 스캔은 구조체마다 `listIdx`를 0으로 되돌리므로 `descGreat.bad[0]`~`descGrim.bad[0]` **5개가 같은 `(Asset, Field, Index)`** 를 받았다.

실측하니 Config는 **374행 → 고유 121개**로, **일곱 자산이 전부** 충돌하고 있었다. 그래서 자산별 구조 파서(`Read-ConfigRows`)를 붙였다. → **374행 → 고유 374개, 충돌 0.**

**키 규칙** — `Config_{짧은자산명}_{경로}`. 경로는 SO 루트부터의 **필드 이름 경로**이고, 구조체 리스트는 위치 대신 **그 구조체가 이미 갖고 있는 식별자**로 주소를 만든다.

> [!important] `StaticID` 칸에는 **짧은 자산명**을 넣는다
> Config SO는 `BaseData`가 아니라 진짜 `StaticID`가 없다. 검사 ⑨는 빈 `StaticID`를 실패로 잡으므로, 대장의 그 칸에 `Seer`·`Tutorial` 같은 짧은 자산명을 싣는다. 그러면 `Get-SoKey`의 Config 분기는 `Config_{StaticID}_{Index}` **한 줄**로 끝난다 — 경로 전체가 이미 `Index` 칸에 들어 있기 때문이다(`Dialogue`의 `choiceText`가 `Index`에 `노드_선택지`를 싣던 것과 같은 방식).

**`SeerConfig` 콜사이트** — `PickRandom`이 번역까지 마친 문장을 돌려주도록 바꿨다(순서가 핵심).

`TutorialConfig.GetLines`는 **살아 있는 `step.lines` 배열을 그대로** 돌려주고, `GetPortraitSprite(IList<string>)`는 `ReferenceEquals(step.lines, lines)`로 어느 묶음이었는지를 되찾는다. 번역한 **사본**을 돌려주는 순간 67개 키 전부가 매칭에 실패하고, `SetPortrait(null)`은 `if (sprite != null)` 가드에 걸려 **직전 초상을 그대로 남긴다.**

**S11에서 잡아낸 것 — 컬렉션의 「에디터 절반」이 빠져 있었다**

사용자가 *"Data 컬렉션은 안 보이는데 무기는 제대로 번역돼서 보이네"* 라고 짚었다. 원인은 `<이름>.asset`(`StringTableCollection`) 누락 — Localization Tables 창은 **이 자산만 보고** 목록을 만드는데, 런타임은 Addressables + Shared Data만 있으면 되므로 정확히 이 증상이 나온다.

**검사 ⑨도 함께 신설했다.** Phase 5 키는 `StaticID`로 런타임에 조립되므로 코드에 문자열이 없어 검사 ④의 시야 밖이다. `StaticID`를 바꾸면 **모든 언어가 조용히 한국어로 되돌아간다.** 대장의 모든 행이 실제 키로 풀리는지 대조하도록 했고, 일부러 키를 깨뜨려 검사가 실제로 실패하는지도 확인했다(63건 검출, exit 1).

**S12에서 잡아낸 것 - 키 규칙이 대화에서 깨졌다**

사용자가 *"아침이벤트는 언어 변환이 안되는데? SpineDialogueView에서부터 한국어 이름으로 나와"* 라고 보고했다. 원인은 회귀가 아니라 **`Dialogue` SO가 아직 미착수**였던 것 - 화자 이름·대사·선택지가 전부 여기서 온다.

그런데 착수하려니 지금까지의 `{종류}_{StaticID}_{필드}` 규칙이 **대화에서는 성립하지 않았다.** `dialogueText`·`speakerName`은 `nodes[]` 안에, `choiceText`는 `nodes[].choices[]` 안에 있어 한 자산에 같은 필드가 여러 번 나온다. 188행 중 고유 키는 166개뿐이었고, 최대 **5개 문자열이 한 키를 공유**했다.

> [!danger] 등장 순서로 번호를 매기면 안 된다
> 한국어가 없거나 빈 노드는 대장에 안 올라오므로, 그 뒤 인덱스가 전부 하나씩 밀린다. 결과는 **다른 노드의 대사가 화면에 뜨는 것**이고, 폴백이 정상 문장을 내보내므로 화면만 봐서는 틀린 줄 모른다.

키 규칙을 확장했다 - `Dialogue_{StaticID}_Node{n}_Text` / `_Node{n}_Speaker` / `_Node{n}_Choice{c}` / `_DefaultSpeaker`.

곁가지로 `dialogueName` 54건이 **표시 콜사이트 0건**(에디터 라벨)임을 확인해 제외했다. 그래서 188 -> **134건**.

**S7에서 감사 도구가 잡아낸 것 — `UNKNOWN_SCRIPT` 판정 신설**

`ScoutProgressItem.prefab`의 두 라벨을 참조하는 MonoBehaviour의 **스크립트 GUID가 Assets에 존재하지 않았다**. 도구는 「참조는 있는데 `.text` 쓰기는 못 찾음」 -> `MISSING`으로 떨어뜨리고 있었는데, 이건 「모른다」이지 「부착해야 한다」가 아니다. 그대로 부착했으면 충돌 위험이 있었다.

#### 한 종류를 처리하는 절차

1. `Audit-SoText.ps1` 실행 -> `so-ledger.csv`에서 해당 `Type` 행을 뽑는다
2. **콜사이트를 먼저 조사한다.** 필드마다 실제 표시 지점을 찾아 `Log.`/에디터 전용/골드 사유 문자열과 구분한다. 표시 지점이 하나도 없으면 제외 후보다 (`$SKIP_FIELDS`에 사유와 함께)
3. **en/ja/zh만** 적은 번역 파일을 `(StaticID, Field)` 키로 만들고, **`ko`는 스크립트가 대장에서 그대로 가져오게 한다**
4. `Add-LocEntries.ps1`로 `Data` 컬렉션에 추가
5. 해당 SO에 `DisplayXxx` 프로퍼티 추가, 콜사이트를 `.필드` -> `.DisplayXxx`로 치환 (**`Log.` 줄과 `SpendGold` 사유는 한국어 원문 유지**)
6. `dotnet build` + `Verify-Localization.ps1` (검사 ⑨가 모든 키가 풀리는지 대조한다)

> [!important] 3번이 이 절차의 핵심이다
> `ko`를 손으로 옮겨 적으면 **한 글자만 달라도 그 자리는 조용히 번역이 안 붙는다**(폴백이 한국어를 내보내므로 화면상 구별 불가). 그래서 번역 파일에는 `ko`를 아예 **적지 않고**, 병합 스크립트가 `(StaticID, Field)`로 대장과 조인하면서
> - 대장에 있는데 번역이 없으면 -> 에러
> - 번역에 있는데 대장에 없으면(오타) -> 에러
>
> 로 양방향 대조한다. 이번 163건은 이 방식으로 **불일치 0건**이었다.

**ID 대역** (`Data`): `1001~` Weapon · `2001~` Dungeon · `3001~` Material · `4001~` ActiveItem · `5001~` VisitorEvent · `6001~` Adventurer(미사용, `Names`로 처리) · `7001~` DungeonEvent · `8001~` Quest · `9001~` Dialogue · `10001~` Config

> [!note] `WeaponData.description`(89) / `MaterialData.description`(48)은 아직 화면에 안 나온다
> 둘 다 코드에 표시 콜사이트가 없다. 그래도 함께 번역해 뒀으므로 나중에 어디선가 쓰기 시작해도 바로 4개 언어가 나온다.
> `VisitorEventData.description`과의 차이는 **의도**다 — 이쪽은 플레이어에게 보일 목적의 설명문(`[TextArea]` 플레이버 텍스트)이고, 저쪽은 `"<이벤트명> 이벤트"`라는 에디터 메모다. 그래서 앞의 둘은 번역하고 뒤는 제외했다.

> [!note] Phase 3에서 만든 **코드 쪽 폴백은 이미 4개 언어로 번역돼 있다**
> `SeerConfig.greetingLines`가 비면 `Seer_GreetingFallback`, `PriceTierConfig.GetMerchantGreeting`이 null이면 `WeaponShop_GreetingFallback`이 나온다. 즉 **SO 풀이 비어 있어도 4개 언어가 성립**하므로, Phase 5는 급하지 않고 종류별로 나눠 진행해도 게임이 깨지지 않는다.

> 이번 작업에서 만든 **코드 쪽 폴백은 이미 번역돼 있다**. 예를 들어 `SeerConfig.greetingLines`가 비면 `Seer_GreetingFallback` 키가 나오고, `PriceTierConfig.GetMerchantGreeting`이 null이면 `WeaponShop_GreetingFallback`이 나온다. 즉 **SO 풀이 비어 있는 상태에서도 4개 언어가 성립**한다.

#### 닉네임 허용 문자 — ja/zh로 넓혔다가 되돌림

**출발점**: `^[가-힣a-zA-Z0-9_]+$` 라서 **일본어·중국어 플레이어가 자기 언어로 닉네임을 쓸 수 없었다.** 기본 닉네임은 `Player{ID앞6자}`라 ASCII이므로 게임은 돌아가지만, 변경하려는 순간 막힌다. 그래서 히라가나(`U+3041~3096`) · 가타카나(`U+30A1~30FA`) · 장음 `ー` · 반복기호 `々` · CJK 통합 한자(`U+4E00~9FFF`)를 더한 패턴으로 넓혔다가, **같은 날 원래 패턴으로 되돌렸다.**

```
^[가-힣a-zA-Z0-9_]+$          <- 현재 (확장 철회)
^[가-힣a-zA-Z0-9_ぁ-ゖァ-ヺー々一-鿿]+$   <- 잠깐 썼던 확장판
```

**철회 이유 1 — 폰트 Static 재베이크와 양립하지 않는다.** [[다국어_도입전략]] 10절의 릴리즈 절차는 ja/zh 폴백 폰트를 **번역 텍스트에 실제로 쓰인 글리프만으로** Static 재베이크하는 것이다. 닉네임은 임의 입력이라 어떤 글자가 올지 미리 뽑을 수 없으니, 재베이크하는 순간 닉네임의 가나·한자는 아틀라스에 없어 전부 두부(□)가 된다. Dynamic을 유지하면 피할 수 있지만 그러려면 소스 TTF **약 19MB**(`GenJyuuGothic-Bold.ttf` 11.0 + `ZCOOLQingKeHuangYou-Regular.ttf` 7.9)를 빌드에 계속 실어야 한다. 현재 AAB가 164.5MB다.

**철회 이유 2 — 허용해도 완전하지 않았다.** 확장 패턴은 CJK 통합 한자 20,992자를 전부 받는데, 두 폰트 cmap의 합집합은 15,150자(72.2%)뿐이다. 나머지 **5,842자(27.8%)는 Dynamic이어도 두부**다. 상용역(JIS 제1·2수준, GB2312)은 커버되지만 벽자(`龘` 등)는 못 그린다.

| | JP 폰트 | SC 폰트 | 합집합 |
|---|---|---|---|
| 히라가나 · 가타카나 · `ー` · `々` | 전부 | 없음 | 전부 |
| CJK `U+4E00~9FFF` (20,992자) | 12,721 | 9,176 | **15,150 (72.2%)** |

**결정**: 19MB와 자국어 닉네임을 맞바꾼 것. 닉네임 하나를 위해 19MB를 얹고도 27.8%는 여전히 깨지는 쪽보다, 영숫자로 제한하는 편이 낫다고 판단했다.

**대신 안내를 명확히 했다.** `Nickname_ErrInvalidChars`가 "허용되지 않은 문자가 포함되어 있습니다"라고만 해서 ja/zh 유저는 무엇을 써야 하는지 알 수 없었다. 4개 언어 모두 허용 범위를 직접 알려주도록 교체했다.

| 로케일 | 변경 후 |
|---|---|
| ko-KR | 한글, 영문, 숫자, _만 사용할 수 있습니다. |
| en | Only Korean, English letters, numbers and _ are allowed. |
| ja | ハングル・英数字・_のみ使用できます。 |
| zh-Hans | 只能使用韩文、英文字母、数字和 _。 |

에러 라벨은 1.5초 유지 후 0.5초 페이드아웃(`NicknameChangePopupView`)이라 더 길게 풀어쓰면 다 읽기 전에 사라진다. "왜 안 되는지"가 아니라 "무엇이 되는지"만 담은 이유다.

**한글 호환 자모**(`ㄱ~ㅣ`)는 원래부터 제외였고 그대로 뒀다(`ㅋㅋㅋ` 방지).

> [!danger] 이 규칙은 **세 곳**에 복사돼 있다 — 어긋나면 「클라는 통과, 서버는 거부」가 된다
> `NicknameConfig.cs`(필드 기본값) · `NicknameConfig.asset`(실제로 쓰이는 값) · `Tools/CloudCode/changeNickname.js`(서버).
>
> **`Tools/CloudCode/sync_profanity.ps1`이 이걸 강제한다.** 원래 금칙어 목록만 밀어 넣던 스크립트를 `MIN_LENGTH`·`MAX_LENGTH`·`ALLOWED_PATTERN`까지 동기화하도록 넓혔고, `-Check` 스위치로 **쓰지 않고 검증만** 할 수 있게 했다(어긋나면 exit 1).
>
> ```powershell
> powershell -File Tools\CloudCode\sync_profanity.ps1 -Check   # 검증만
> powershell -File Tools\CloudCode\sync_profanity.ps1          # 서버 파일 갱신
> ```
>
> 규칙을 바꾸면 **에셋만 고치고 이 스크립트를 돌린 뒤 `changeNickname.js`를 재배포**한다.

> [!warning] 이 스크립트는 삭제돼 있었다
> `changeNickname.js`의 주석은 「목록 변경 시 `sync_profanity.ps1` 실행」이라고 안내하는데, 정작 그 파일이 `0d61244a`(code inspection)에서 **삭제된 상태**였다. 복구하면서 두 가지 결함도 같이 고쳤다.
> - **CRLF에서 아예 동작하지 않았다** — `^const PROFANITY_WORDS = \[.*\];$` 의 `$`가 .NET 다중행 모드에서 `\n` 앞만 매칭하므로, `core.autocrlf=true`로 체크아웃된 CRLF 파일에서는 「line not found」로 중단됐다
> - 그걸 `\r?$`로 고쳤더니 이번엔 `\r`을 **소비**해 그 줄만 LF가 되어 파일에 줄바꿈이 섞였다(`Attach-Lse.ps1`에서 겪은 「줄바꿈 전멸」과 같은 계열). **전방탐색**(`(?=\r?$)`)으로 바꿔 해결
>
> 고친 뒤 「주입 -> 검출(exit 1) -> 복구 -> 바이트 동일」까지 확인했다.

**검증**: `sync_profanity.ps1 -Check` exit 0으로 세 사본이 일치함을 확인했다. 축소 후에는 `冒険者`·`简体`가 거부되고 `테스트123`·`Player_01`이 통과한다.

> [!warning] 이미 등록된 닉네임은 재검증되지 않는다
> `changeNickname`은 **새로 바꿀 때만** 검사한다. 확장 패턴이 살아 있던 동안 가나·한자로 등록한 계정이 있다면 그 닉네임은 서버에 그대로 남고, 재베이크 후 리더보드에서 두부가 된다. `getPlayerNicknames`로 조회해 확인할 것.

> [!danger] 남은 위험: **금칙어가 한국어 전용이다** (5,033단어)
> 허용 문자를 넓혔으므로 **ja/zh 욕설은 무필터**로 통과한다. 서버 `BanManager`가 사후 수단이다. 목록 추가는 사용자가 직접 처리하기로 했다(2026-08-03).

#### 폰트 전략 — Static 재베이크 범위 (실측 후 결론)

닉네임을 ja/zh로 열면서 **「Static 재베이크」의 범위**를 정해야 했다. 실제 숫자를 뽑아서 답을 냈다.

**게임이 실제로 쓰는 고유 문자 수** (테이블 6종 x 4로케일 + SO 한국어 전부 합집합)

| 로케일 | 고유 문자 | 내역 |
|---|---|---|
| `ko-KR` | 862 | ASCII 76 + 한글 786 |
| `en` | 85 | ASCII만 |
| `ja` | 1,123 | 한자 888 + 가나 149 + ASCII 74 |
| `zh-Hans` | 1,538 | 한자 1,451 + ASCII 73 |
| **ja+zh 합집합** | **2,074** | **한자 1,835 + 가나 149** |

**용량 환산** (`KERISKEDU_B` 실측 기준 3.3KB/글자)

| 방식 | 글자 수 | 용량 | 비고 |
|---|---|---|---|
| **실사용 문자만** | 1,984 | **~6.4MB** | 정확히 필요한 것 |
| 상용한자(일본 상용 2,136) | 2,136 | ~6.9MB | 중국어를 못 덮는다 |
| 통용규범 1급(중국 3,500) | 3,500 | ~11.3MB | 일본어를 못 덮는다 |
| **ja+zh 상용 합집합** | ~7,500 | **~24MB** | 실사용의 **3.8배** |

> [!important] 결론: **둘 다 아니다 — 지금 구성이 이미 맞다. ja/zh 폰트를 Static으로 바꾸지 마라.**
>
> 현재 상태 (2026-08-03 실측)
>
> | 폰트 | 모드 | 구워진 문자 | 소스 TTF |
> |---|---|---|---|
> | `Maplestory Light` (ko 기본) | **Static** | 11,326 | - |
> | `GenJyuuGothic-Bold` (ja 폴백) | **Dynamic** | 634 | 11.6MB 포함 |
> | `ZCOOLQingKeHuangYou` (zh 폴백) | **Dynamic** | 460 | 8.3MB 포함 |
>
> ja/zh가 **Dynamic**이고 `ClearDynamicDataOnBuild=0`, 소스 TTF도 함께 들어간다. 즉 **아틀라스에 없는 글자는 런타임에 즉석에서 래스터화된다** — 플레이어가 입력한 임의의 한자를 포함해서. 닉네임 문제는 이미 해결돼 있다.
>
> **「상용 한자 통째로」는 두 가지를 동시에 잃는다**
> - **크다** — 게임에 한 번도 안 나오는 글자까지 담아 ~24MB. 실사용만 구우면 6.4MB다
> - **그런데도 닉네임을 못 덮는다** — 사람 이름에는 상용 목록 밖 한자가 흔하다(`喆`·`玥`·`昱`). **덩치를 4배로 키우고도 원래 목적인 두부(□) 방지에 실패한다**
>
> 열거 **가능한** 것(게임 텍스트)은 미리 굽고, 열거 **불가능한** 것(플레이어 입력)은 Dynamic에 맡기는 게 맞다. 지금 구성이 정확히 그것이다.
>
> **한국어만 전체 Static인 이유**: 한글 완성형은 11,172자로 **닫혀 있어** 전부 굽는 게 가능하다. CJK는 2만 자가 넘어 같은 수를 못 쓴다. 이게 처리가 갈리는 유일한 이유다.

> [!warning] 지금 프리베이크는 게임 텍스트를 **다 덮지 못한다** (동작은 정상)
> `be964b87` 재베이크 뒤에도 ja는 634/1,123, zh는 460/1,538만 구워져 있다. Dynamic이라 나머지는 런타임에 그려지므로 **화면은 정상**이고, 비용은 처음 뜰 때의 짧은 지연뿐이다.
>
> 문제는 그 다음이다 — 커밋 메시지는 「안 하면 새 번역문이 두부로 뜬다」로 읽히는데, 실제로는 Dynamic이 덮어주고 있었을 뿐이다. **여기서 「다 구웠으니 Static으로 바꾸자」로 가면 게임 텍스트 절반과 닉네임 전부가 동시에 깨진다.**
>
> 지연까지 없애고 싶으면 `Export-FontCharset.py`가 뽑아 주는 **정확한 목록**(`out/charset/ja.txt` 1,123자 / `zh-Hans.txt` 1,538자)으로 프리베이크하면 된다. **모드는 Dynamic 그대로 두는 것이 핵심이다.**

#### 약관·개인정보 — **번역하지 않기로 결정 (2026-08-03)**

`DataCollectionView`가 `TextAsset` 2개(`TermsOfService.txt` 134줄 / `PrivacyPolicy.txt` 91줄)를 인스펙터로 물고 `bodyText.text = doc.text` 한 줄로 표시한다. 제목만 `UI_Screens` 키로 번역돼 있다.

> [!important] 결정: **본문은 한국어 원문만 유지한다** — 코드 변경 없음
> 기술 작업 자체는 작았지만(`LocalizedAsset<TextAsset>` + Asset Table 1개), 본문 225줄이 **법적 문서**라 기계 번역본을 게시하면 책임 소재가 생긴다. 세 선택지(① 한국어만 ② 번역본 + 「충돌 시 한국어본 우선」 조항 ③ 언어별 법무 검토본) 중 **①**을 택했다.
>
> **따라서 `LocalizedAsset<TextAsset>` 전환은 하지 않는다.** 지금 구조가 곧 결정된 상태이고, 이 항목은 닫힌다. 나중에 ②로 바꾸려면 이 문단부터 다시 읽으면 된다.

## 4-A. 모험가 이름 (2026-08-02 완료)

일반 모험가 이름 198개를 `Names` 컬렉션으로 옮겼다.

- **씬**: `InGameScene`의 `VisitorManager` 이름 풀 3개가 한국어 이름 -> **키**(`Name_M_001` 등)로 바뀌었다. 인스펙터에서 계속 추가/삭제할 수 있고, 항목은 테이블 키를 적는다
- **저장**: `AdventurerInstance.nameKey`를 세이브에 굽는다. `Name` 프로퍼티가 키를 현재 언어로 조회하므로 **언어를 바꾸면 이미 등장한 모험가 이름도 함께 바뀐다**
- **구버전 세이브**: `nameKey`가 없으므로 기존 `instanceName`(한국어)을 그대로 쓴다 - 깨지지 않는다
- **네임드**: `nameKey = "Name_" + StaticID` 규칙으로 조회한다(`Name_ADV_NAMED_001` 등 10개). SO는 손대지 않았으므로 **CSV 임포터 영향 없음**. `adventurerName`은 폴백 겸 에디터 확인용으로 남는다
- **구버전 세이브의 네임드**: 복원 시 `StaticID`로 키를 되살리므로 번역이 적용된다(일반 모험가는 어떤 이름이었는지 알 수 없어 한국어 유지)
- **이름 교체**: Tolkien 고유명사 8개 + 드로고 -> 드로칸, 총 9개를 한국어 풀 포함 전면 교체했다

**이름을 추가할 때**: `Names` 테이블에 키 추가(4개 언어) -> 씬의 해당 풀에 키 추가. 두 곳이 어긋나면 `No translation found`가 화면에 뜬다.
**네임드를 추가할 때**: `Name_<StaticID>` 키를 `Names`에 추가한다. 빠뜨리면 이름 자리에 에러 문구가 뜬다.

## 4-B. 모험가 방문 대사 (2026-08-02 완료)

`AdventureDialogueView`의 대사 213줄을 `Dialogue` 컬렉션으로 옮겼다.

- **SO**: `VisitorConfig`의 6개 풀(첫방문/호감도 4단계/호감도 만렙) x 남녀 = 12개 리스트가 한국어 원문 -> **키**(`Adv_First_M_001` 등)로 바뀌었다
- **코드**: `VisitorManager.PickRandomLine`이 키를 뽑아 현재 언어로 조회한다. 폴백 6개도 키(`Adv_Fallback_*`)
- 첫 방문 남 59 / 여 54, 나머지 5개 풀은 각각 남 10 / 여 10

> 한국어는 존댓말/하오체/하게체를 섞어 쓰는데 영어엔 대응 개념이 없어 **남녀 대사 23쌍이 영문에서 동일**해진다. 각 모험가는 성별 풀 하나만 뽑으므로 실사용에는 문제없다.

**대사를 추가할 때**: `Dialogue` 테이블에 키 추가(4개 언어) -> `VisitorConfig`의 해당 풀에 키 추가.
