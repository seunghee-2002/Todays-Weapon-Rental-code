# 아키텍처

> [!abstract] 한 줄 요약
> **4계층**(Data / Manager / View / Controller) + **싱글턴 매니저** + **Observer 이벤트**. 매니저는 View를 모르고, View는 도메인 매니저를 Controller 경유로만 만진다.

## 4계층 구조

```
Data         ScriptableObject (*Data), RuntimeInstance (*Instance), SaveData (*SaveData)
Manager      BaseManager<T> 싱글턴 - 비즈니스 로직만 (Scripts/Systems/, 부트스트랩은 Scripts/Core/)
View         BaseView - 표시만, 비즈니스 로직 없음 (Scripts/UI/Views/)
Controller   BaseController<TView> - View <-> Manager 중개 (Scripts/UI/Controllers/)
```

### 계층 호출 규칙

| 호출 | 허용 | 비고 |
|---|:---:|---|
| View -> Controller | ✅ | 도메인 매니저는 **반드시** Controller 경유 |
| View -> `DataManager` | ✅ | 정적 SO 카탈로그, **읽기 전용** |
| View -> `AnalyticsManager` | ✅ | 관측 전용(게임 상태 미변경). 컨트롤러가 없는 View(하단바, 아침 이벤트 9종)가 `btn_clicked`를 발행하기 위함 -> [[버튼_이벤트]] |
| View -> 그 밖의 도메인 매니저 | ❌ | Controller를 거친다 |
| Controller -> Manager + View 갱신 | ✅ | |
| Manager -> 다른 Manager | ✅ | |
| Manager -> View / Controller | ❌ | **절대 참조하지 않는다** |

## 핵심 패턴 5가지

### 1. Singleton — `BaseManager<T>`

모든 Manager는 `BaseManager<T>`를 상속하고 `T.Instance`로 접근한다.

```csharp
// Scripts/Systems/ 에 위치
public class InventoryManager : BaseManager<InventoryManager> { }

// 사용
InventoryManager.Instance.AddWeapon(...);
```

표준 매니저 형태:

```csharp
public class XxxManager : BaseManager<XxxManager>
{
    public event Action<Type> OnSomethingChanged;
    public void Initialize(GameData gameData) { }
    public void SaveToGameData(GameData gameData) { }
}
```

### 2. MVC — UI 레이어

- **View** (`BaseView`) — UI 패널 표현. `Open()` / `Close()` / 이벤트 구독
- **Controller** (`BaseController<TView>`) — View <-> Manager 중개. 콜백 이름은 `On + 행위`
- **Model** — Manager + `GameData`(한 회차) / `PlayerData`(영구)

-> [[UI_구조]]

### 3. Observer — C# `event Action<>`

Manager가 이벤트를 발행하고 UI·다른 Manager가 구독한다.

```csharp
TimeManager.Instance.OnTimeChanged += handler;        // (int hour, int minute)
InventoryManager.Instance.OnWeaponAdded += handler;
ReputationManager.Instance.OnReputationChanged += handler;
```

### 4. Data Holder — ScriptableObject

정적 데이터는 SO, 런타임 데이터는 Instance 클래스로 분리한다.

- 정적: `WeaponData`, `AdventurerData`, `DungeonData` (`Scripts/Data/StaticData/`)
- 런타임: `WeaponInstance`, `AdventurerInstance`, `AdventureInstance` (`Scripts/Data/RuntimeInstance/`)

-> [[데이터_구조]] · [[데이터_접근_원칙]]

### 5. Partial Class

덩치 큰 Manager는 **매니저 이름의 하위 폴더**에 기능별로 파일을 분할한다.

| 매니저 | 분할 |
|---|---|
| `AdventureManager/` | `.cs` + `.Calculations` + `.EventProcessor` + `.Sequence` + `.Mood` |
| `VisitorManager/` | `.cs` + `.Spawn` + `.Npc` + `.Instance` |
| `Insight/InsightManager` | `.cs` + `.Reveal` + `.Visibility` |

> [!important] 거대 매니저의 내부 모듈 추출은 현 시점 보류
> 성공률 계산기·이벤트 진행기·스폰 정책 분리 같은 deepening은 **하지 않는다.** partial 분할 패턴을 그대로 유지한다.
> 변경 시 회귀 위험이 크고, 자동 테스트 인프라가 없는 상태에서 큰 구조 변경은 후순위다.
>
> 또한 `VisitorManager -> ReputationManager`(`GetAdventurerSpawnInterval`, `GetEventChance`) 호출은 **단방향이고 도메인 의미가 명백한 정상 호출**이다(양방향 의존 아님).

## 코딩 스타일

| 항목 | 규칙 |
|---|---|
| 필드 | `[SerializeField] private` — public 필드 금지, `_` 접두사 금지 |
| 이름 | 클래스/메서드/enum은 PascalCase, 필드는 camelCase |
| 네임스페이스 | 모든 스크립트에 `namespace TodaysWeaponRental` |
| 로그 | `Debug.Log($"[ClassName] 메시지");` |
| Region | `#region 초기화` / `#region View로부터 호출되는 메서드` / `#region 이벤트 핸들러` / `#region 내부 메서드` |

## 시간 이벤트 구독 규칙

> [!important] 매니저 간 발화 순서에 의미를 두지 않는다
> `TimeManager`의 `OnTimeChanged` / `OnDayChanged` / `OnPhaseChanged` 구독자들 간에는 **발화 순서 제약을 두지 않는다.**
> "Daytime 진입 시 `QuestBoardManager`가 의뢰판을 갱신한 뒤 `VisitorManager`가 모험가를 스폰" 같은 매니저 간 시간 이벤트 의존은 **없다.**

함의:

- 매니저들은 `+=` / `-=`로 **독립 구독**한다.
- 등록 순서가 발화 순서를 결정하지만, 그 순서에 **도메인 의미를 부여하지 않는다.**
- 새 매니저가 시간 이벤트를 구독해도 다른 매니저의 동작에 영향을 주지 않도록 설계한다.
- 따라서 **페이즈 게이트(중앙 dispatcher) 같은 응축 모듈은 도입하지 않는다.**
